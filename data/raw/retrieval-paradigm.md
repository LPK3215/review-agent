## 一、一条轴：理解放在写入端还是查询端

六种形态的分歧可以压到一处：**理解在什么时候发生**。

- **写入端**＝入库时就把理解做完，查询时直接读。
- **查询端**＝入库只存原文，查询时现算。

每往写入端移一格：查询便宜一分，错误被固化一分，语料变更后的重建成本涨一分。

> 选型的实质不是挑最先进的检索，是挑你愿意在哪一端犯错。

这条轴的价值在于，它把「你用过哪些 RAG 方案」这种清单式提问，变成「你在哪一端做权衡」的结构式回答。

| 形态 | 理解的时点 | 检索单元 |
|---|---|---|
| 向量 RAG | 查询端 | 片段 |
| Contextual Retrieval | 查询端（索引时补块） | 片段 + 位置说明 |
| GraphRAG | 写入端（预计算摘要） | 关系 |
| LightRAG | 写入端（动态增量） | 关系 + 向量 |
| 文档树导航 | 索引端（结构先行） | 章节 |
| LLM-Wiki | 写入端（理解全部前置） | 概念页 |
| OpenViking | 换一层 | 目录树 |

## 二、六种形态逐条

### 2.1 向量 RAG

- **结论**：在模型参数之外另存一份可查的索引。索引负责找，原文负责读。它改变的不是模型能力，是「谁负责记住事实」——从权重交给外部存储。
- **候选与差异**：与微调的差别是知识可热插拔，改知识不用重训；与长上下文的差别是每次只带相关片段，成本不随总量线性涨。2020 年那篇 RAG 论文的出发点不是「检索更准」，是知识密集型任务打不过专门训练的模型、给不出来源、没有更新通道。
- **代价与边界**：块是切出来的，切的那一刻它就和上下文断了。向量还原不成原文（数字、人名、条件在压缩时丢），所以索引必须同时存原文与向量。单跳事实强，跨章节取证、跨文档追关系、全局归纳三类任务全露短板。
- **证据**：Lewis et al.《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》NeurIPS 2020，[arXiv:2005.11401](https://arxiv.org/abs/2005.11401)。NQ 上 626M 参数的 RAG 做到 44.5 EM，11B 闭卷 T5 只有 34.5——参数不是知识的好容器，索引才是。

### 2.2 Contextual Retrieval

- **结论**：不改变检索机制，只在索引时给每个块补一段 50–100 token 的位置说明（这份文档叫什么、属于哪一章、这一段在讲谁）。补的是「块自己是谁」——这层信息是切块时丢的，检索期再怎么调权重也补不回来。
- **候选与差异**：与普通向量 RAG 的差别只在索引管道多一步 LLM 调用。三个做法可叠加：位置说明、上下文 BM25、rerank，叠得越多降幅越大。它是补丁，不是路线。
- **代价与边界**：一次性 $1.02 / 百万 document token，且必须靠 prompt caching 才成立。官方测的是英文语料，中文要重测。补不了块与块之间的关系。
- **证据**：Anthropic 2024-09-19《Introducing Contextual Retrieval》。top-20 块检索失败率：基线 5.7% → 3.7%（仅上下文嵌入，降 35%）→ 2.9%（+上下文 BM25，累计 49%）→ 1.9%（+rerank，累计 67%）。**报 1.9% 时必须说明是三者齐上。** 机制与四条工程要点见 [[02-AI/AI专项/文档处理与RAG/文档处理与RAG总纲|总纲]] 13.10。

### 2.3 GraphRAG

- **结论**：把摘要从查询时的临场发挥，改成索引时的预计算。抽实体建图、按关系密度聚成社区、每圈预写摘要，社区摘要相当于物化视图。
- **候选与差异**：与向量 RAG 的差别是从「找相似片段」变成「沿关系追查」，另加一条全局归纳能力。它真正治的不是多跳，是「这批材料的主题是什么」——这类问题本质是摘要任务而不是检索任务，答案不在任何一块里。
- **代价与边界**：建图贵、查询贵、语料必须静态。实测 600 token 窗口、约 100 万 token 语料、16GB 虚拟机，建图 281 分钟；全局查询 20 秒起，单次读几十万 token。它只对「把全文塞进上下文」省钱，对向量检索是纯增量。单跳细节型问题上，论文自己承认向量 RAG 更强。
- **证据**：Edge et al.《From Local to Global: A Graph RAG Approach to Query-Focused Summarization》，[arXiv:2404.16130](https://arxiv.org/abs/2404.16130)；[microsoft/graphrag](https://github.com/microsoft/graphrag)（MIT）。**注意：该仓未归档、2026-11-09 仍有推送、README 无维护模式声明**，所以「不上图」的正当理由是「不到 500 页」或「问题不是全局归纳类」，不能拿「仓库停维护」当理由。

### 2.4 LightRAG

- **结论**：解决的不是 RAG 的老问题，是 GraphRAG 自己造成的问题——新数据一进来社区划分就变，原摘要整批作废。做法是把新抽的节点集、边集与旧的取并集，是 INSERT 不是重建。
- **候选与差异**：宏观能力来源与 GraphRAG 相反。GraphRAG 靠索引时预写的摘要（静态、稳定、贵），LightRAG 靠查询时把问题拆成主题词与实体词两路打图（动态、便宜，代价是结论随关键词漂）。
- **代价与边界**：首建不便宜，同样要逐块抽实体，量级与 GraphRAG 抽取阶段相当；增量会让图越来越稠，要定期合并剪枝。对 GraphRAG 的 Overall 胜率四个领域 54.8% / 52.0% / 52.8% / **49.6%**，第四个领域是输的——「全面超越」不成立。
- **证据**：Guo et al.《LightRAG》EMNLP 2025，[arXiv:2410.05779](https://arxiv.org/abs/2410.05779)；[HKUDS/LightRAG](https://github.com/HKUDS/LightRAG)（MIT，40,645★，2026-11-11）。同规模新数据整体重建约 1,399 万 token（1,399 社区 × 2 遍 × 每份约 5,000 token）。细节见总纲 13.11。

### 2.5 文档树导航

- **结论**：检索单元是章节。不建向量不切块，把文档解析成结构树，模型自己选章节、读原文、不够再补一章。
- **候选与差异**：把「一次召回」换成「多步阅读」。专治答案散在相隔几十页的多个章节里、只召回最相似那段就会漏前置条件的场景。
- **代价与边界**：只适合章节清晰的长文档（年报、合同、手册、接口文档）。延迟高、token 花得多，建树同样会出错，扫描件要先解决解析与 OCR。通常当副手，不当唯一通道。
- **证据**：[VectifyAI/PageIndex](https://github.com/VectifyAI/PageIndex)，MIT，自述 vectorless、reasoning-based；机制见总纲 13.6。

### 2.6 LLM-Wiki

- **结论**：理解全在入库时做完，产物是页面而不是索引。三层：raw 只读、wiki 由模型独占写、schema 定规则；三个动作：ingest、query、lint。
- **候选与差异**：与 RAG 是编译与解释的差别。RAG 每次提问重新推导、不留痕；Wiki 编译一次、之后只改受影响的十几页，知识会累积。读取不靠相似度，从索引页沿交叉链接走。有个容易说错的点：Karpathy 那份 gist 只是能贴给 AI 的 idea file，原文强调「这是想法不是实现」；「编译器 vs 解释器」是 AWS 博客的引申，不是他提的。
- **代价与边界**：四种失败模式。① 并发会碎：65 份 PDF 并发导入生成 245 页，38% 语义重复且各自增量后分叉；② 编译会失真：盲编译灾难性失败率 53%–60%，加对照诊断能找回八成；③ 查询不一定便宜：语料仅 24 篇的预注册实验测出查询 token 约为 RAG 的 21 倍；④ 物理上限：索引就是 `index.md`，204 页时已 2.8 万 token。另外编译没消灭检索——只靠目录选页命中率 70.0%，加一条 BM25 到 92.7%。
- **证据**：Karpathy [llm-wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)（2026-04）；标准化格式为 Google Cloud 2026-06-12 发布的 [OKF v0.1](https://okf.md/)；机制见总纲 13.7。

### 2.7 OpenViking：换一层，不是第七条路线

- **结论**：`viking://` 下开一棵虚拟文件系统——`resources/` 放文档与代码（你说的知识库就是这一个目录）、`memories/` 放偏好与经验、`skills/` 放怎么做任务。每个目录自动生成两层摘要（一句话 + 结构与要点），原文按需才读；检索先定位目录或子树，再往下钻。
- **候选与差异**：前面几条回答「这批知识怎么被找到」，它回答「Agent 知道的所有东西怎么放进一个能管的空间」。知识只是其中一个目录。
- **代价与边界**：AGPL-3.0 商用分发要过法务、要独立起服务、依赖嵌入与视觉模型提供方、官方未公开十万级文件下的延迟与成本；LoCoMo 上自报的准确率提升是自家模型组合跑的，无第三方复现。
- **证据**：[volcengine/OpenViking](https://github.com/volcengine/OpenViking)（AGPL-3.0，41,984★，2026-11-11）；见总纲 13.13。

## 三、成本与失效数字（面试可背）

| 形态 | 关键数字 | 关键失效 |
|---|---|---|
| 向量 RAG | NQ 上 626M 参数 RAG 44.5 EM vs 11B 闭卷 T5 34.5 | 块切出来就断上下文，相似不等于完整 |
| Contextual Retrieval | 5.7%→3.7%→2.9%→1.9%；$1.02 / 百万 document token | 补不了块间关系，依赖 prompt caching |
| GraphRAG | 约 100 万 token 建图 281 分钟；全局查询 20 秒起 | 双贵、语料须静态、单跳不如 RAG |
| LightRAG | 同规模重建 1,399 万 token；检索 <100 token/次；Overall 胜率 54.8/52.0/52.8/49.6 | 结论随关键词漂，首建不贵是误解 |
| 文档树导航 | 多步阅读，token 随跳数线性涨 | 只认结构清晰的文档 |
| LLM-Wiki | 65 PDF → 245 页（38% 重复）；盲编译失败 53–60%；查询 token ≈ RAG 的 21 倍；204 页目录 2.8 万 token | 并发碎、编译失真、目录有上限 |
| OpenViking | 41,984★ · AGPL-3.0 | 商用许可、需起服务、无第三方复现 |

**成本估算的正确姿势**：按抽取 token 量乘模型单价，先算建库一遍的账，再乘预计重建次数。图类方案的账几乎全落在「重建」上，不在「查询」上。

## 四、怎么选：三问，顺序不能换

**先数页数，再看问题形态，最后看知识性质。**

```
Q1 知识库多大？
├─ < 200,000 token（约 500 页）→ 整库塞进上下文，不做 RAG
│    └─ 唯一例外：要的是可审核的编译产物 → LLM-Wiki
└─ ≥ 500 页 ↓

Q2 问题是什么形态？
├─ 单跳事实（某条规定怎么写）        → 向量检索 + rerank
├─ 检索常漏、块里缺主语              → + Contextual Retrieval
├─ 要「整体判断」且语料静态          → GraphRAG（当方法论，别当基础设施）
├─ 数据天天变又要关系推理            → LightRAG（并集增量）
└─ 答案散在相隔几十页的多个章节      → 文档树导航（当副手）

Q3 知识是什么性质？
├─ 广而新                            → 向量 RAG
└─ 少而精、准而深                    → LLM-Wiki（甜区几百页内、有负责人审核）

再上一层：如果真实问题是「Agent 上下文怎么管」→ 选上下文系统（OpenViking 这类），
前面所有检索方案都降格成它 resources/ 一个目录里的选项。
```

一句话记住：**不到 500 页别选边；过了 500 页按问题形态选；要复利才上 Wiki。**

## 五、混合方案与治理

稳妥解是混合：先查 wiki 目录，编译过的页面命中就直接用，未覆盖的退回向量检索。前者便宜、可审核，后者覆盖广但每次都要重新理解一遍。

两条配套动作：

- **标出处类型**：回答里注明每条结论是「审核过的页面」还是「原始检索」，两者可信度不一样。这一步做了，混合方案才不是拼接。
- **定负责人**：最常被漏掉的角色是谁对编译产物负责。没人负责，错误会以「看起来很权威」的形式沉下来。

治理成本是融合方案里最容易被低估的一项：同一条知识在片段、图节点、文档树、Wiki 页里各存一份，源内容或权限一改，四处都要同步失效。很多方案停在演示阶段就是卡在这里。

## 六、面试口径

### 30 秒版

> 这类方案的区别只有一条轴：理解放在写入端还是查询端。RAG 全在查询端，块一切出来就断上下文；Contextual Retrieval 在索引时给块补位置说明，补的是块自己是谁；GraphRAG 把摘要预计算进图，补的是整体判断，代价是 100 万 token 建图 281 分钟、语料必须静态；LightRAG 用并集增量解决更新贵，代价是结论随关键词漂，而且它对 GraphRAG 只是打平，胜率第四个领域 49.6% 是输的；LLM-Wiki 把理解全前置成页面，代价是并发会碎、目录有上限。所以判据是三步：先数页数，不到 500 页根本不上这些；再看问题形态；最后看知识性质。

### 两分钟版骨架

1. 先给轴，不给清单。
2. 每条只说三件事：补哪个洞、主要代价、何时选。
3. 抛一条硬数字当锚（281 分钟 / 1.9% / 500 页任选其一）。
4. 收尾给判据：先数页数 → 看问题形态 → 看知识性质。
5. 主动补混合方案 + 出处标注，显示你想过治理。

### 高频追问

| 追问 | 应答要点 |
|---|---|
| 为什么不用 GraphRAG？ | 两条理由任选：① 语料不到 500 页，整库塞上下文更好；② 问题不是全局归纳类。别只说「太重」。 |
| GraphRAG 贵在哪？ | 不是代码，是跑：逐块调 LLM 抽实体，查询要读几十万 token。给 281 分钟。 |
| LightRAG 比 GraphRAG 强吗？ | 不强，几乎打平。Overall 胜率 54.8/52.0/52.8/49.6，第四领域是输的。它真正的价值是增量更新便宜。 |
| Contextual Retrieval 属于哪一层？ | 索引期补丁，不是检索路线。失败率降幅要报三档，1.9% 是加上 rerank 之后。 |
| LLM-Wiki 和 RAG 冲突吗？ | 不冲突，不同层。Wiki 是知识组织形态，RAG 是检索结构。稳妥解是 Wiki 命中优先、RAG 兜底。 |
| 长上下文都 1M 了还要 RAG 吗？ | 要。窗口大解决「放不下」，不解决「该放什么」；全塞的成本随轮次线性涨。 |
| 你怎么防止错误沉淀？ | 说治理：谁审核、来源类型标注、失效同步。「没人负责的项目别上 Wiki」这句很加分。 |

## 七、核实与边界

| 项 | 情况 |
|---|---|
| 已回源核对 | arXiv 三篇论文编号与标题；Anthropic 博客五个数字（5.7/3.7/2.9/1.9、$1.02、200,000 token ≈ 500 页）；GraphRAG 281 分钟（论文 HTML 正文，600 token 窗口 / Podcast 语料 / 16GB VM）；LightRAG Overall 胜率四领域原表；OpenViking 与 LightRAG 仓库的 star、许可、归档状态（GitHub API，2026-11-11） |
| 未逐条复算 | GraphRAG「单次全局查询读几十万 token、几百次调用」；LLM-Wiki 那组数字（出自 AWS 中国博客，本次未访问）；Karpathy gist（GitHub API 三次 502，未当场复核，沿用库内 2026-04-04 记录） |
| 一处纠偏 | 原文称 GraphRAG 仓库「已进维护模式」不成立，实测未归档、2026-11-09 仍有推送、README 无该声明。本节与 2.3 已按核实结果改写 |
| 未采纳的表述 | 原文「16 步」类编号式说法未出现于本文；本文不写流程步数 |
