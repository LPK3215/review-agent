## 要点与方案对比

---

### 检索范式：六种形态不是六选一

- **结论**：六者的分歧只有一条轴——理解放在**写入端**还是**查询端**。写入端＝入库时把理解做完，查询时直接读；查询端＝入库只存原文，查询时现算。每往写入端移一格，查询便宜一分、错误被固化一分、语料变更后的重建成本涨一分。选型的实质不是挑最先进的检索，是挑你愿意在哪一端犯错。
- **候选与差异**：它们不在同一层。向量 RAG、GraphRAG、LightRAG 是检索结构；Contextual Retrieval 是挂在向量 RAG 上的索引期补丁；文档树导航是文档内部的导航结构；LLM-Wiki 是知识的组织形态；OpenViking 换了一层，把知识库降格成 Agent 上下文里的一个目录。把它们混成一排比优劣，就会得出「RAG 过时了」这种错结论。
- **代价与边界**：组合的代价是治理。同一条知识在片段、图节点、文档树、Wiki 页里各存一份，源一改就要同步失效四处，这是最容易被低估的成本。另一个边界是人的成本：没人对编译产物负责的项目不要上 Wiki。
- **证据**：判据、成本数字与面试答法独立成篇，见 [[02-AI/AI专项/文档处理与RAG/检索范式选型-六种形态与理解的时点|检索范式选型：六种形态与理解的时点]]；机制、参数与成本测算见 [[02-AI/AI专项/文档处理与RAG/文档处理与RAG总纲|文档处理与RAG总纲]] 13.4 至 13.13。本节只留速查表与判定三步，不重复展开。

| 形态 | 理解的时点 | 何时选 |
|---|---|---|
| 向量 RAG | 查询端 | 500 页以上、单跳事实、广而新 |
| Contextual Retrieval | 查询端（索引时补块） | 检索常漏、块里缺主语 |
| GraphRAG | 写入端（预计算摘要） | 要整体判断且语料静态 |
| LightRAG | 写入端（动态增量） | 数据天天变又要关系推理 |
| 文档树导航 | 索引端（结构先行） | 答案散在相隔几十页的多个章节 |
| LLM-Wiki | 写入端（理解全部前置） | 500 页内、有负责人审核、知识要复利 |
| OpenViking | 换一层 | 真实问题是「Agent 上下文怎么管」 |

**判定三步**：先数页数（不到 200,000 token，约 500 页，就别上 RAG）→ 再看问题形态 → 最后看知识性质。每条形态的补洞、代价、原论文数字与追问答法，见 [[02-AI/AI专项/文档处理与RAG/检索范式选型-六种形态与理解的时点|检索范式选型]]。

#### 融合的四条路

- **结论**：按任务路由，不按技术栈站队。四条路按代价从低到高：向量找入口再走图扩展、向量定位文档再用树深读、Wiki 存核心加长尾 RAG、Wiki 反哺其他模式。
- **候选与差异**：第四条最容易忽略但收益最快，整理好的 Markdown 比原始 PDF 更好切、更好抽关系。路由可以让模型选工具，也可以用 LangGraph 把标准流程固化。
- **代价与边界**：难点不在技术，在治理。源内容或权限一变，片段、图、Wiki 页、文档树都要跟着失效；跨通道必须用元数据对齐身份与版本。
- **证据**：四条路径见 [[02-AI/AI专项/文档处理与RAG/文档处理与RAG总纲|总纲]] 13.8；混合落地的出处标注与负责人两条，见 [[02-AI/AI专项/文档处理与RAG/检索范式选型-六种形态与理解的时点|检索范式选型]] 第五节。

### 检索、语义、执行：三层不是一条演进线

#### Ontology 不是 GraphRAG 的下一版

- **结论**：这是三层，不是一条演进线。RAG 与 GraphRAG 回答「怎样取证」，Ontology 回答「业务对象怎样表达、允许怎样改变」。上了本体，文档证据仍然要检索，业务操作仍然要由具体服务执行——两者可以在同一系统里组合，不存在谁替代谁。
- **候选与差异**：**通用本体**（[W3C OWL 2](https://www.w3.org/TR/owl2-overview/)）定义类、属性、个体与形式语义，提供的是建模能力，推不出审批、审计或业务系统回写。**厂商运营本体**（[Palantir Ontology](https://www.palantir.com/docs/foundry/ontology/overview/)）是产品定义，语义部分给对象/属性/关系，执行部分给 Action Types 与 Functions，再叠平台权限、应用限制与治理。把产品能力当成「本体」这个词的通用含义，是最常见的误读。
- **代价与边界**：一项业务动作能否执行取决于四件事——定义了规则、绑定了实现、配置了权限、底层系统支持。只把对象命名清楚，一步都没到。维护成本落在数据映射、业务逻辑、权限与执行集成上，是业务与数据治理的投入，不是模型的能力。跨系统对象、关系与治理都复杂时才有收益；简单场景先把对象与业务服务接口明确就够。
- **证据**：两类 MCP 的入口分工与三项自检清单见 [[02-AI/AI专项/文档处理与RAG/文档处理与RAG总纲|总纲]] 13.14；动作契约的写法见 [[02-AI/AI知识库/工具调用与FunctionCalling|工具调用与 Function Calling]]，三类权限分开管见 [[02-AI/AI知识库/用户与鉴权|用户与鉴权]]。

### 文档解析

#### 解析方案（MinerU / pdfplumber / PyMuPDF / Docling）

- **MinerU Hybrid（Pipeline本地 + VLM走Qwen-VL API）**
  - 对应项目：ESG-Extractor
  - 优势：表格/版面还原好、复杂PDF友好
  - 劣势：VLM依赖外部API、成本与延迟高
  - 适用场景：真实企业PDF、含大量表格图文混排
- **LightRAG / Neo4j 图谱抽取**
  - 对应项目：Yuxi
  - 优势：保留实体关系、利于推理
  - 劣势：不擅长精确原文还原
  - 适用场景：知识图谱型问答

#### 扫描件（图片型PDF）处理

- **PaddleOCR 3.7.0 PP-OCRv6（GPU加速）注入**
  - 对应项目：ESG-Extractor
  - 优势：中文OCR强、可注入原解析流程
  - 劣势：需额外脚本、增加链路
  - 适用场景：扫描件/图片型PDF
- **仅 VLM 识别**
  - 对应项目：ESG-Extractor（Hybrid的VLM部分）
  - 优势：上下文理解好
  - 劣势：贵、慢
  - 适用场景：少量关键页

#### 表格/图片/代码块怎么保护结构

- **ESGStructureAwareNodeParser（自研，保护表格结构）**
  - 对应项目：ESG-Extractor
  - 优势：表格不被切断、指标可对齐
  - 劣势：需针对ESG表格定制
  - 适用场景：结构化指标抽取

### 向量存储与检索

#### 向量库选型

- **Milvus（HNSW索引 + 版本化）**
  - 对应项目：ESG-Extractor
  - 优势：分布式、GPU、大规模、生产可用
  - 劣势：运维重（etcd/MinIO/Pulsar）
  - 适用场景：73份报告、生产级

#### 检索策略（纯向量/关键词/混合）+ 融合方式

- **混合检索 + HyDE + HNSW**
  - 对应项目：ESG-Extractor
  - 优势：召回质量高、HyDE提升语义召回
  - 劣势：链路复杂、需调参
  - 适用场景：高精度指标抽取

#### 混合检索该怎么配

- **结论**：两路召回、RRF 融合、再叠一层交叉编码器重排，是当前默认配置。向量管语义改写，BM25 管精确串，RRF 绕开两路量纲不同的问题，重排负责把「像」变成「对」。
- **候选与差异**：融合有三种做法。RRF 只看名次，稳但会把弱路的尾部噪声一起带进来；加权求和要归一化分数，权重还得按语料调；学习式融合（如 LambdaMART）效果最好，但要有标注数据。重排也有三条路：不做，排名噪声原样进 prompt；云 API，省事但有候选数上限和网络依赖；本地 BGE 系列，可控但要 GPU。
- **代价与边界**：多一路索引与一层精排，延迟与维护成本都上升；中文分词不补专有词，BM25 对业务黑话基本无效；语料全是同义改写型问法时，BM25 增量接近零。RRF 的 k 不是准确率旋钮，调它改变的是名次衰减速度。
- **证据**：机制、参数与可运行代码见 [[02-AI/AI专项/文档处理与RAG/文档处理与RAG总纲|文档处理与RAG总纲]] 第七章 7.8 至 7.11；RRF 出自 Cormack 等 2009 年 SIGIR 论文，k=60 是社区沿用的经验值。

#### Rerank / Top-K

##### 已经排过序了，为什么还要 Rerank

- **结论**：粗排是**一维**的——query 和文档各自压成一个向量，只比一条轴上的距离，两边零交互；Rerank 是**二维**的——query 和文档拼成一条序列进同一个模型，每个 token 和对方每个 token 互相 attend，比的是关系不是距离。一维只能判断「像不像」，二维才能判断「这个条件成不成立」。向量维度拉多高都一样，那只是把同一条轴拉长。
- **候选与差异**：粗排（双塔）离线预算 + ANN 索引，全库毫秒级，query 只面对一个定长向量；精排（cross-encoder）逐对现场前向，不进索引，换来两边 token 可见；第三条路是 late interaction（ColBERT），token 级向量先预算好、查询时做 MaxSim，准度接近精排、成本接近粗排。
- **代价与边界**：延迟随候选数线性涨，只对 top-20~50 做；输入长度受限（bge-reranker-v2-m3 上限 8192 token 但官方推荐训练长度 1024，更早的 base/large 是 512），超长 chunk 要切小；召回阶段没捞出来的精排救不回；多跳问题单条打分不够。
- **证据**：2026-10-23 按 bi-encoder / cross-encoder 公开评测与 BAAI 模型页核对后整理；本库项目仍是「建议补强」状态，线上只有混合检索 + HyDE 的召回层。

##### Top-K 怎么定

- **结论**：先粗排放大召回（top-50 起），再精排收敛到进 prompt 的 3~8 条。
- **候选与差异**：K 小 → 漏召回，生成时没有依据；K 大 → 噪声进上下文，稀释注意力、拉高成本。
- **代价与边界**：有 Rerank 时 K 可以放大（多给精排喂候选）；没有 Rerank 时 K 放大会直接掉准确率。
- **证据**：对应各项目，经验值需按场景实测调。

### 检索策略（2026-11-01 补）

- 解决什么问题：ESG 报告里同一个指标有多种说法，同时又有一批精确串，单路召回两头都顾不全。
- 为什么选这个（候选方案是什么）：向量加 BM25 两路召回走 RRF，再叠重排。没有引框架，四个函数自己手搓，链路短、出问题能一眼定位是哪一路。
- 代价（放弃了什么）：多一路索引与一层精排，延迟上升；BM25 要维护分词词典，新出现的指标名得补进去。
- 边界（什么情况下失效）：语料全是同义改写型问法时 BM25 没有增量；候选数超过重排上限要先截断；分块把表格切断，两路都救不回来。

### 知识底座形态（2026-11-09 并入）

- 解决什么问题：自己这套库和项目文档要被 Agent 反复读、反复引用，且内容每天在变。
- 为什么选这个（候选方案是什么）：现在事实上的形态就是 LLM-Wiki。raw 是 `Clippings/` 与各项目目录，wiki 是 `02-AI` 与 `01-Tutorial` 的正文，schema 是 `AGENTS.md` 与各级 README，ingest 由 AI 会话执行，lint 靠两个链接校验脚本。没建向量库，因为规模只有千余篇，grep 加链接导航够用。
- 代价（放弃了什么）：放弃语义召回，提问方式要贴合库里的用词；跨文档关系靠人工反链，机器不能自动追多跳。
- 边界（什么情况下失效）：超过几千篇、或要回答「谁依赖谁」这类多跳问题时失效，那时先补向量层做召回，再考虑图。

### 检索范式选型（2026-11-11 并入）

- 解决什么问题：同一批语料，问「某条规定怎么写」和问「这批材料的共同风险是什么」，一套向量检索只能答前半类。
- 为什么选这个（候选方案是什么）：按问题形态路由，不按技术栈站队。低于 500 页不做 RAG；单跳走向量加 rerank；块缺主语加 Contextual Retrieval；要整体判断且语料静态才上图；知识要复利才建 Wiki。统一依据是理解的时点。
- 代价（放弃了什么）：每多一条通道就多一份治理，源一改四处失效；Wiki 还要有人对编译产物负责。
- 边界（什么情况下失效）：语料天天变，图路线整批重建，成本落回重建端；没有审核人的项目上 Wiki，错误会以权威口吻沉淀。
