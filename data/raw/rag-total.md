## 一、RAG 是什么，解决什么问题

### 1.1 定义

RAG 是检索增强生成，Retrieval-Augmented Generation。三个词就是三个动作：先从外部知识库检索相关片段，再把片段增强进提示词，最后由模型生成答案。

它不是一种模型，也不是一个框架，而是一种系统组装方式：模型不变，把「它该知道什么」从参数里搬到每次调用时的上下文里。

### 1.2 传统大模型的三道坎

| 坎 | 具体表现 | 为什么模型自己解决不了 |
|---|---|---|
| 知识过时 | 训练数据有截止日期，问最近发生的事就答不上或答错 | 权重是训练时快照，不会自己更新 |
| 幻觉 | 编出听起来合理但不存在的事实、条款、数字 | 模型优化的是「像真的」，不是「是真的」 |
| 知识盲区 | 不知道企业私有文档、内部制度、专业手册 | 这些内容从没进过训练集 |

RAG 对三者的解法是同一个：把答案的依据放在提示词里，让模型做「阅读理解」而不是「回忆」。

### 1.3 RAG 带来的五个变化

- 事实性提高。答案有出处，模型编造的动机下降。
- 可溯源。能指出答案来自哪份文档的哪一段。
- 更新即生效。改知识库，下一次提问就是新内容，不用重训。
- 成本低于微调。注入知识不需要 GPU 训练。
- 私有数据不出库。文档留在自己服务器，只把片段塞进请求。

### 1.4 RAG 与微调、长上下文怎么选

| 方案 | 适合什么 | 代价 | 典型误用 |
|---|---|---|---|
| RAG | 知识频繁变、要给出处、文档在外部 | 多一条链路要维护，效果受切分与召回限制 | 拿它做风格与格式约束，白费力气 |
| 微调 | 固定语气、固定输出结构、领域话术 | 知识进权重，改一次重训一次，难溯源 | 用它灌知识，最后发现查不到出处 |
| 长上下文 | 文档不多、一次读完就够 | 成本随长度涨，中段注意力衰减 | 拿它替代检索，几十份文档就撑不住 |

判断三问：知识多久变一次；答案要不要给出来源；文档总量有多大。变、要、多，选 RAG。不变、不要、少，可以长上下文。要的是表达方式而不是事实，才走微调。

三者可以叠加。工程上最常见的组合是 RAG 供事实、微调管风格。

### 1.5 适用与不适用

适合：企业知识库问答、产品手册客服、法规与合同检索、研报与财报解读、教育与答疑、代码仓库问答。

不适合：需要实时交易决策的场景（延迟不可控）、完全无结构且无标注的语料（切不准）、要求 100% 准确的合规结论（检索只能降低风险，不能担保）。

### 1.6 三条架构路线

| 路线 | 流程 | 控制力 | 延迟 | 适合 |
|---|---|---|---|---|
| 2-Step RAG | 先检索、再生成，固定两步 | 高 | 稳定、快 | FAQ、文档问答 |
| Agentic RAG | 检索变成工具，由 Agent 决定调不调、调几次 | 低 | 不定 | 多工具研究助手 |
| Hybrid RAG | 查询增强加检索验证加答案验证 | 中 | 中等且不定 | 领域问答，要质量控制 |

起步一律走 2-Step。原因是它能被同一批输入量化：换一个切分策略，指标变化能归因。Agentic 的检索次数不固定，做对照时说不清是策略好还是多搜了几轮。

## 二、完整链路

### 2.1 三个模块

| 模块 | 职责 | 出错时的表现 |
|---|---|---|
| 检索器 | 从库里找出与问题相关的片段 | 答案没有依据，或依据是旧版本 |
| 增强器 | 把片段与问题组装成提示词 | 塞太多挤掉指令，塞太少缺上下文 |
| 生成器 | 基于提示产出答案 | 忽略资料自由发挥，或答非所问 |

### 2.2 在线七步，逐步写清

**第一步，查询处理。** 把用户问题转成向量，或转成关键词，或两者都做。多轮对话里先做指代消解，把「它」「这个」换成具体名词。

**第二步，相似度检索。** 在向量库里按距离取出 Top-K 候选。度量方式必须与建索引时一致，否则分数的量纲完全不同。

**第三步，结果重排，可选。** 用交叉编码器对候选逐条打分重排。候选数一般控制在 20 到 100 之间，再多延迟不可接受。

**第四步，上下文组装。** 把片段拼成一段，带编号与出处，控制在预算内。重要片段放在开头或结尾，避开中段。

**第五步，生成回答。** 提示词里写死三条：只依据资料、没有就说没有、标注来源编号。

**第六步，后处理，可选。** 事实核查、格式整理、把编号换成可点击的引用。

**第七步，返回。** 附来源列表。严肃场景里，无来源的答案视为不可用。

### 2.3 离线索引管道

```text
原始文档
  → 加载（本地文件、网页、数据库、对象存储）
  → 解析（PDF/Word/HTML 转成结构化文本）
  → 清洗（去页眉页脚、合并断行、保留标题层级）
  → 分块（按结构或长度切成片段）
  → 向量化（Embedding 模型逐块编码）
  → 入库（写向量库并建 ANN 索引）
```

这六个环节里，解析与分块决定了检索的上限。后面再怎么重排，也只能在已经入库的候选里挑。很多人把力气全花在换 Embedding 模型上，结果解析把表格切碎了，换模型也没用。

### 2.4 三种相似度度量

| 度量 | 计算的是 | 什么时候用 | 注意 |
|---|---|---|---|
| 余弦相似度 | 两个向量的夹角，忽略长度 | 文本语义检索的默认选择 | 向量已归一化时与内积等价 |
| 欧氏距离 | 空间中的直线距离 | 位置本身有意义的场景 | 未归一化时会被长度差异主导 |
| 内积 | 方向乘以长度 | 推荐类场景，长度是信号 | 文本检索里长文本会占便宜 |

归一化的作用：把向量除以其模长，长度信息被抹掉，只比方向。文本检索通常都做这一步。

### 2.5 一个能跑通的最小链路

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter
from pymilvus import MilvusClient

splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(docs)
client = MilvusClient(uri="./rag_demo.db")
client.create_collection("docs", dimension=1024)
for i, ch in enumerate(chunks):
    client.insert("docs", {"id": str(i), "vector": embed(ch.text), "text": ch.text})

def ask(q, k=3):
    hits = client.search("docs", data=[embed(q)], limit=k)
    ctx = "\n\n".join(h["entity"]["text"] for h in hits[0])
    return llm(f"只依据资料回答，没有就说资料不足。\n资料：\n{ctx}\n问题：{q}")
```

这段代码的价值在于把七步压缩成看得见的四行：切块、入库、检索、生成。缺任何一行都不能算跑通。

## 三、解析：文档怎么变成文本

### 3.1 为什么解析是第一个决胜点

模型看到的不是 PDF，是文本。解析错了，后面全错且无法补救：表格塌成一行，指标与数值分家；双栏 PDF 被按行读，左右栏串成一句；扫描件没做 OCR，整页空白。

### 3.2 六种输入的解析做法

| 输入 | 工具与做法 | 常见问题 |
|---|---|---|
| TXT、Markdown | 直接读取，按标题切分 | 几乎没有 |
| Word | python-docx 一类，取段落与标题样式 | 页眉页脚、批注、目录混入正文 |
| HTML | 正文提取算法去导航与广告 | 代码块与表格被压平 |
| 电子版 PDF（有文本层） | pdfplumber、PyMuPDF 逐页抽文本与坐标 | 双栏串行、表格塌陷 |
| 图文混排 PDF | MinerU 一类版面模型，分区还原表格与图 | 慢，要 GPU 或外部 API |
| 扫描件 | 先 OCR（PaddleOCR 一类），再走文本链路 | 识别错字变成检索噪声 |
| 图片、图表 | 多模态模型生成描述后入库 | 描述质量决定能否被召回 |

### 3.3 表格必须单独保护

表格是 RAG 里最容易翻车的地方。按字符数硬切时，表头与前几行可能落在上一个块，数据落在下一个块，检索命中后只剩一堆数字，没有列名。

做法三条：解析阶段识别表格边界；切分阶段把整张表作为一个块，或按行切且每行重复表头；入库时把表名、列名写进块文本，让向量能匹配到「这张表在讲什么」。

### 3.4 清洗三件事

- 去掉页眉页脚与页码。它们会出现在每个块里，形成高频噪声词，BM25 会把它们当强相关特征。
- 合并被换行切碎的句子。PDF 常把一句话拆成三行，不合并会让语义切分失效。
- 保留结构标记。标题层级、编号、列表符号是后续按结构切分与引用定位的前提。

### 3.5 中文文档的四个特殊问题

| 问题 | 表现 | 处理 |
|---|---|---|
| 分词边界 | 专有名词被切碎，BM25 召不到 | 维护领域词典，或用字符级 BM25 |
| 全角半角 | 同一符号两种写法，向量与关键词都分不清 | 入库前统一归一化 |
| 段落无标点 | 长句连成一段，语义切分找不到断点 | 改用结构切分或加标点预处理 |
| 表格跨页 | 跨页表格被切成两个块 | 解析时按续表标识合并 |

### 3.6 解析质量的验收

不验收就入库，是后面所有「召回不准」的根源。三条验收：

- 随机抽二十页，看正文是否连续、有无串栏。
- 抽五张表格，看表头与数据是否在同一个块里。
- 抽三个扫描页，看 OCR 错字率，超过阈值就换模型或加预处理。

## 四、分块：把长文档切成可检索的片段

### 4.1 为什么必须切

三个理由同时成立：模型上下文装不下整库；整篇文档压成一个向量会把局部语义摊薄，问题问的是一句，向量代表的是全文；片段越短，检索越准，但上下文越不全。分块就是在这对矛盾里取平衡。

### 4.2 九种策略，逐种写清

**一、固定长度切分。** 按字符或 token 数硬切，相邻块留重叠。

```python
def fixed_chunk(text, size=500, overlap=50):
    out, i = [], 0
    while i < len(text):
        out.append(text[i:i + size])
        i += size - overlap
    return out
```

优点实现简单、块大小一致；缺点会在句子中间断，术语被切断后两半都召不回。适合快速验证与结构完全混乱的文本。

**二、滑动窗口。** 与固定长度同一类，重点在重叠量。重叠的作用是让跨块的信息至少在一个块里完整出现。重叠 10% 到 20% 够用，设成半块会让索引体积翻倍。

**三、递归字符切分。** 按分隔符优先级逐级降级：先按双换行（段落）切，切不动再按单换行，再按句号问号，最后才按空格。

```python
splitter = RecursiveCharacterTextSplitter(
    chunk_size=700, chunk_overlap=150,
    separators=["\n\n", "\n", "。", "！", "？", " ", ""],
)
```

这是工程默认选。它不保证语义完整，但保证尽量在自然边界断开，成本极低。

**四、语义切分。** 先把文档拆句，逐句算向量，相邻两句相似度低于阈值就在此切断。

```python
def semantic_chunk(sents, th=0.5):
    vecs = model.encode(sents)
    out, cur = [], [sents[0]]
    for i in range(1, len(sents)):
        if cos(vecs[i - 1], vecs[i]) < th:
            out.append("".join(cur)); cur = [sents[i]]
        else:
            cur.append(sents[i])
    out.append("".join(cur))
    return out
```

优点边界最合理；缺点要额外跑一遍 Embedding，成本和耗时都上升。适合课程转录、访谈记录这类口语化长文。

**五、按结构切分。** 用文档自身的结构：Markdown 的标题层级、HTML 的标签、PDF 的章节号。

```python
def md_chunk(md):
    parts = re.split(r"\n(?=#{1,3}\s)", md)
    return [p for p in parts if len(p) > 80] or [md]
```

优点是切出来的块天然对齐章节，引用时能说出「出自第三章第二节」。缺点依赖解析质量，扫描件没有结构可用。

**六、父子文档。** 建两层：父块保留完整章节，子块是父块里的小段，都入库，子块记录父块 ID。检索命中子块，取回父块进上下文。

**七、Small-to-Big。** 父子文档的检索策略表述：检索用小块求准，生成用大块求全。

```python
def expand(hits, store):
    parents = {h["parent_id"] for h in hits}
    return [store[p] for p in parents]
```

代价是索引体积翻倍，且父块过长时会把噪声带回上下文，需要再截断一次。

**八、分层索引。** 建三层索引：句子级、段落级、文档级。先在细层检索，命中不足再往粗层要摘要。适合「先定位在哪一节，再读那一节」的问答模式。

**九、Agentic 分块。** 让模型读一遍文档，输出分块方案（起止位置、主题、理由），再按方案切。

代价最高，每次入库都要跑模型。只在结构极不规范、且文档量不大的语料上值得试。

### 4.3 参数怎么定

| 参数 | 经验值 | 依据 |
|---|---|---|
| chunk size | 512 到 1024 token | 技术文档偏小保证精度，法规合同偏大保证完整 |
| overlap | 50 到 100 token | 约 10%，防边界切断 |
| 块内元数据 | 来源、页码、章节路径、文档 ID | 引用溯源与元数据过滤都靠它 |
| 每块最小长度 | 100 字以上 | 太短的块语义不完整，易成噪声 |

### 4.4 按文档类型选型

| 文档类型 | 策略 | 块大小 | 重叠 |
|---|---|---|---|
| Markdown 技术文档 | 按结构切加滑动窗口 | 512 到 1024 | 50 到 100 |
| 学术论文 | 递归切分加 Small-to-Big | 512 到 1024 | 100 到 200 |
| 聊天记录、访谈 | 语义切分 | 动态 | 无 |
| 法规、合同 | 定长加父子文档 | 300 到 500 | 50 到 100 |
| 代码仓库 | 按函数或类切 | 单函数级 | 无 |
| 快速验证 | 固定长度 | 512 | 50 |

### 4.5 分块的五个坑

| 坑 | 后果 | 处理 |
|---|---|---|
| 全库一个参数 | 合同被切碎、网页留大块 | 按文档类型分组配参数 |
| 表格被切断 | 列名与数据分家 | 表格整体成块 |
| 无重叠 | 关键句落在边界，两边都缺 | 加 10% 重叠 |
| 块过长 | 噪声进上下文，注意力被稀释 | 上限硬约束，超出走父子块 |
| 不带元数据 | 命中后说不出来源 | 入库时写入来源与页码 |

## 五、Embedding：决定能不能被找回

### 5.1 它在链路里的位置

Embedding 把文本映射到向量空间，语义相近的文本距离近。它同时作用于入索引与查询两端：两端必须用同一个模型、同一套预处理，否则向量不在同一空间，检索结果等于随机。

### 5.2 选型五看

| 看什么 | 具体口径 |
|---|---|
| 任务类型 | 在 MTEB 榜上看 Retrieval 那一列，别拿分类或聚类的分数选检索模型 |
| 语言覆盖 | 中文语料选中文优化模型；中英混排选多语言模型 |
| 维度 | 768 到 1024 是常见平衡点；3072 精度略高，但存储翻倍、检索变慢 |
| 最大输入 | 要与块大小匹配。上限 512 的模型喂 1024 的块会被截断 |
| 部署方式 | 本地部署数据不出库、可控；调 API 省事但有配额与合规问题 |

常见选择：通用中文 bge-large-zh 一类；通用英文 text-embedding-3 系列；轻量验证 bge-base 一级；多语言 gte 或 m3 一类。

实践顺序：先用轻量模型把链路跑通，指标达标后再换大模型，看提升是否值得那份成本。

### 5.3 维度不是越高越好

维度高带来两点：精度略高；存储与检索成本线性上升。一万篇文档每个块 1024 维，与 3072 维相比，存储差三倍，检索延迟也差一截。除非评测显示低维明显掉分，默认取中位。

### 5.4 领域失配

通用模型在专业语料上常见三种失配：术语向量挤在一起，问「心肌梗死」召不回「AMI」；问法与原文措辞差距大；同义实体多写法，向量分不清是同一个。

判断方法：抽二十对「问题与应命中的片段」，看 Top-5 命中率。低于六成就先怀疑 Embedding，别急着改切分。

### 5.5 微调怎么做

用对比学习，三元组是查询、正样本、负样本。

```python
from sentence_transformers import SentenceTransformer, losses
model = SentenceTransformer("bge-base-zh")
train_loss = losses.TripletLoss(model)   # (query, pos, neg)
```

数据构造三条：正样本是真正能回答问题的片段，不是主题相近的片段；负样本要难，取语义相近但不相关的；正负比 1 比 4 到 1 比 9。

代价：要造标注；微调后模型与索引绑定，换模型必须整库重建。

### 5.6 增量更新

| 做法 | 做法细节 | 代价 |
|---|---|---|
| 全量重建 | 清库重算 | 大库耗时，期间不可用 |
| 按文档 ID 定点替换 | 删该文档所有块，写新块 | 要维护稳定文档 ID |
| collection 版本化 | 新建一版，验收后切流量 | 空间翻倍，但可回滚 |

只加不删是最常见的错误：旧内容留在库里，新内容也在，检索时两版一起被召回，模型拿到的可能是过期条款。

## 六、向量库：存与取

### 6.1 七个库怎么选

| 库 | 特点 | 什么时候用 | 注意 |
|---|---|---|---|
| Milvus | 分布式、支持标量过滤、生态成熟 | 生产、千万级以上 | 运维重，需要 etcd 与对象存储 |
| Qdrant | Rust 实现、过滤强、部署轻 | 中等规模私有部署 | 生态比 Milvus 小 |
| FAISS | 纯库，无服务，算法最全 | 研究、单机、自建索引 | 无持久化服务，要自己管 |
| Chroma | 轻量易用 | 原型与小项目 | 规模上万后性能下降 |
| Pinecone | 全托管 | 不想运维 | 数据出库，成本高 |
| Weaviate | 原生混合检索 | 要图谱与混合检索 | 学习曲线略陡 |
| Elasticsearch | 已有 ES 基础设施 | 不想再引组件 | 向量能力不如专用库 |

判断顺序：先看规模，再看要不要自己运维，最后看已有基础设施能不能复用。

### 6.2 五种索引

| 索引 | 原理 | 速度 | 精度 | 适合 |
|---|---|---|---|---|
| Flat | 暴力比对全量向量 | 最慢 | 最高 | 小库、精度优先 |
| IVF | 先聚类，查询时只搜最近的几个桶 | 中 | 中高 | 中等规模 |
| HNSW | 分层图，逐层导航到最近邻 | 最快 | 高 | 当前默认 |
| PQ | 向量量化压缩 | 快 | 中 | 内存吃紧的超大库 |
| DiskANN | 索引落盘 | 中 | 中高 | 十亿级，内存装不下 |

### 6.3 Milvus 完整用法

```python
from pymilvus import MilvusClient
client = MilvusClient(uri="./milvus_demo.db")
client.create_collection(
    collection_name="rag",
    dimension=1024,
    index_params={"metric_type": "COSINE", "index_type": "HNSW",
                  "params": {"M": 16, "efConstruction": 128}},
    segment_row_limit=50000,
)
for i, ch in enumerate(chunks):
    client.insert("rag", {"id": str(i), "vector": embed(ch), "text": ch, "src": path})
hits = client.search("rag", data=[embed(q)], limit=10, output_fields=["text", "src"],
                     search_params={"metric_type": "COSINE", "params": {"ef": 256}})
```

三处必须对齐：`dimension` 与 Embedding 模型输出维度一致；`metric_type` 建库与查询一致；`output_fields` 要带上正文与来源，否则命中后还得回查。

### 6.4 三个调优参数

| 参数 | 作用 | 调大的后果 |
|---|---|---|
| `M` | 每个节点的连边数 | 精度升，内存涨；常见 16 到 64 |
| `efConstruction` | 建索引时的搜索广度 | 索引质量升，建库变慢；常见 128 到 512 |
| `ef` | 查询时的搜索广度 | 召回升，延迟涨；线上主要调这一个 |

线上只调 `ef`，因为前两个改了要重建索引。`ef` 一般设为 `limit` 的 4 到 10 倍起步，再按召回与延迟曲线定。

### 6.5 分区与过滤

分区按业务或时间切，检索时指定分区名可显著缩小搜索范围。分区键选错，等于白做：比如按文档类型分区，但查询总是跨类型，那就没有收益。

标量过滤比后置过滤高效得多。先过滤再检索，结果数量少一个数量级；检索后过滤，等于白算。

### 6.6 选型的现实建议

单机验证用 Chroma 或 FAISS，一天能跑通。上生产用 Milvus 或 Qdrant，差别在运维复杂度与生态。已有 Postgres 且规模不大，pgvector 能省一个组件，代价是索引算法不如专用库丰富。

## 七、检索：召回与融合

### 7.1 三种召回

| 方式 | 原理 | 强在哪 | 弱在哪 |
|---|---|---|---|
| 稀疏检索 BM25 | 词频与逆文档频率，倒排索引 | 专名、型号、编号、法条号 | 换个说法就召不到 |
| 密集检索 向量 | 双塔编码后比距离 | 语义改写、同义表达 | 精确串、数字、罕见词 |
| 混合检索 | 两路候选合并后融合 | 兼顾两者 | 多一路索引与融合逻辑 |

### 7.2 BM25 怎么算

```python
def bm25(q, doc, N, avgdl, df, k1=1.5, b=0.75):
    s = 0
    for t in q:
        if t not in doc:
            continue
        tf, dl = doc[t], sum(doc.values())
        idf = log((N - df[t] + 0.5) / (df[t] + 0.5) + 1)
        s += idf * (k1 + 1) * tf / (tf + k1 * (1 - b + b * dl / avgdl))
    return s
```

三个变量决定行为。`idf` 让常见词权重低、罕见词权重高；`k1` 控制词频饱和，一个词出现十次不等于权重十倍；`b` 控制文档长度归一化，长文档不会因为词多就占便宜。

中文必须先分词。专有词不在词典里，BM25 对这个词等于失明。这是中文 RAG 里 BM25 效果不如英文的主因。

### 7.3 RRF 融合

```python
def rrf(result_lists, k=60):
    score = {}
    for rs in result_lists:
        for rank, doc_id in enumerate(rs):
            score[doc_id] = score.get(doc_id, 0) + 1 / (k + rank + 1)
    return sorted(score, key=score.get, reverse=True)
```

只看名次，不看分数。好处是绕开两路分数不可比的问题：余弦相似度是 0 到 1，BM25 是无上界，直接相加等于让 BM25 支配结果。

`k` 默认 60。它调的是名次衰减速度，不是准确率旋钮：k 大则高位与低位的差距被压平，融合更平均；k 小则靠前的结果权重更集中。

### 7.4 加权融合与学习式融合

| 做法 | 本质 | 代价 |
|---|---|---|
| RRF | 只排名次 | 弱路的尾部噪声一起带进来 |
| 加权求和 | 分数归一化后按权重相加 | 权重按语料调，换数据集就失效 |
| 学习式排序 | 训练排序模型学融合权重 | 要标注数据，维护成本高 |

三种里 RRF 的性价比最高：实现十行、无需标注、对量纲不敏感。代价是它无法利用「某一路明显更可信」这类先验。

### 7.5 两路都不做阈值会怎样

候选集被噪声撑满。向量总会返回 Top-K，哪怕全是无关片段；BM25 也总会返回有词命中的结果。不设阈值，重排阶段就要在几百条噪声里挑，延迟上去、精度还降。

做法：给每一路设最低分阈值，低于阈值的丢弃；再限制融合后的候选总量。

### 7.6 查询侧四种加工

| 手法 | 做什么 | 代价 | 什么时候用 |
|---|---|---|---|
| HyDE | 让模型先编一段假设答案，用这段去检索 | 生成跑偏会带偏检索 | 问法与原文措辞差距大 |
| 查询改写 | 把口语问题改成检索友好的表述 | 多一次模型调用 | 用户提问短、指代多 |
| 查询拆分 | 一个复合问题拆成几个子问题分别检索 | 调用次数翻倍 | 问题里含两个以上诉求 |
| 查询扩展 | 补同义词、上下位词 | 容易扩进噪声 | 术语多写法、缩略语多 |

判断顺序：先试改写，再试拆分，HyDE 放最后。改写最便宜且收益最稳；HyDE 收益大但风险也大。

### 7.7 元数据与隔离

先按元数据过滤再检索，比检索后过滤省一个数量级。常见过滤维度：文档类型、时间范围、部门、权限级别。

多库隔离三种做法。

| 做法 | 隔离强度 | 代价 |
|---|---|---|
| 独立 collection | 最强 | 管理成本随租户数线性上升 |
| 命名空间 | 强 | 部分库支持不完整 |
| 元数据字段 | 弱，靠代码保证 | 一条漏过滤就是越权 |

### 7.8 五种关键词做法对比

| 方法 | 原理 | 要模型 | 速度 | 部署成本 | 适合 |
|---|---|---|---|---|---|
| TF-IDF | 词频乘逆文档频率，纯统计 | 否 | 极快 | 零 | 教学、极小语料 |
| BM25 | TF-IDF 加词频饱和与长度归一 | 否 | 极快 | 零 | 订单号、专有名词、精确数字 |
| Elasticsearch | 内核仍是 BM25，外加分词、高亮、集群 | 否 | 快 | 中，要维护服务 | 大规模生产 |
| SPLADE | 模型把文档映射成稀疏向量，自动挑词赋权 | 是 | 中 | 中 | 想兼具速度与语义 |
| ColBERT | 查询与文档切 token 向量，检索时延迟交互 | 是 | 慢 | 高，吃内存 | 语料大、精度要求极高 |

学习与本地部署选 BM25，零依赖、毫秒级、结果可解释，调参只有两个旋钮。生产环境已有 ES 就直接用 ES 的 BM25，不用再引一套。

`rank_bm25` 的 BM25Okapi 默认 k1=1.5、b=0.75，多数中文语料直接可用。要调的典型场景是文档长度差异极大，比如短 FAQ 与长年报混在一个库里。

### 7.9 四段流程与可运行实现

一次提问走四段：向量路取 topM、BM25 路取 topN、RRF 融合成 topP、Rerank 精排取 topK 进提示词。M 与 N 要给得比最终 K 大，K 通常 3 到 8。粗排负责召回率，精排负责准确率。

```python
import jieba
from rank_bm25 import BM25Okapi

tok = lambda s: [t for t in jieba.lcut(s) if t.strip()]
bm25 = BM25Okapi([tok(t) for t in docs.values()])

def bm25_search(q, top_n=10):
    scores = bm25.get_scores(tok(q))
    best = float(scores.max()) if len(scores) else 0.0
    if best <= 0:
        return []                        # 全零时直接返回，别让阈值失效
    ranked = sorted(zip(docs, scores), key=lambda x: -x[1])
    return [d for d, s in ranked[:top_n] if s >= best * 0.3]

def rrf(result_lists, k=60, top_n=5):
    sc = {}
    for rs in result_lists:
        for r, d in enumerate(rs, start=1):
            sc[d] = sc.get(d, 0.0) + 1.0 / (k + r)
    return [d for d, _ in sorted(sc.items(), key=lambda x: -x[1])[:top_n]]

def hybrid(q, k=3):
    return rerank(q, rrf([vector_search(q), bm25_search(q)], top_n=5), top_n=k)
```

三条边界必须知道：`vector_search` 要换成真实向量库查询并同样做阈值；BM25 全零时必须提前返回，否则 `best * 0.3` 仍是 0，所有文档都能过阈值；Rerank 要能降级，一个超时不该打断整条链路。

### 7.10 四组对照怎么设计

只换检索策略，其他全部固定，才能说明混合检索带来多少提升。

- 四组：只向量、只 BM25、向量加 BM25 走 RRF、再叠 Rerank。
- 固定项：同一语料、同一分块、同一 Embedding 模型、同一份测试问题集、同一个 top-k 口径。
- 指标：命中率（正确答案出现在 top-k 内的比例）、MRR（正确项平均排第几）、端到端答案准确率。
- 取点：top-k 至少跑 3、5、10 三档，看曲线不看单点，否则调大 k 总能把命中率刷上去。
- 结论形态：不写「混合更好」，写「精确串类问题上涨了 X 个点，改写类问题没动，重排把 top-3 又抬了一档」。

### 7.11 六个坑

| 坑 | 后果 |
|---|---|
| 两路都不过阈值就融合 | 尾部噪声淹没真正相关的条目 |
| 中文不分词按空格切 | BM25 直接失效 |
| 分词不补专有词 | 业务黑话永远命中不了 |
| 把 RRF 的 k 当调参旋钮反复试 | 效果波动多半来自阈值与候选数，不在 k |
| 候选数超过 Rerank 服务上限 | 被静默截断，不知道自己丢了什么 |
| 只做混合不做重排 | 粗排的排名噪声原样带进提示词 |

## 八、重排：把「像」变成「对」

### 8.1 为什么必须重排

粗排是一维的：查询与文档各自编码成一个向量，只在一个方向上比距离，两边没有任何交互。精排是二维的：两者拼成一条序列进同一个模型，每个 token 与对方每个 token 互相注意，判断的是「这个条件成不成立」。

一维只能回答像不像，二维才能回答对不对。把向量维度拉到 3072，也只是把同一条轴拉长。

### 8.2 三种编码结构

| 结构 | 计算方式 | 速度 | 精度 | 阶段 |
|---|---|---|---|---|
| 双塔 Bi-Encoder | 查询与文档独立编码，离线预算向量 | 快 | 中 | 粗排 |
| 交叉 Cross-Encoder | 联合编码，逐对现场前向 | 慢 | 高 | 精排 |
| 迟交互 ColBERT | token 级向量，查询时做 MaxSim | 中 | 高 | 折中方案 |

### 8.3 重排代码

```python
from FlagEmbedding import FlagReranker
reranker = FlagReranker("BAAI/bge-reranker-base", use_cpu=True)

cands = vector_db.search(embed(q), top_k=20)
pairs = [[q, c["text"]] for c in cands]
scores = reranker.compute_score(pairs)
final = [c for c, _ in sorted(zip(cands, scores), key=lambda x: x[1], reverse=True)[:5]]
```

流程是 100 粗排、20 精排、5 进上下文。候选越多延迟越高，所以精排只对少量候选做。

### 8.4 重排模型怎么选

| 模型 | 部署 | 特点 | 代价 |
|---|---|---|---|
| bge-reranker-base | 本地 | 性价比较好，中英双语 | 要 GPU 或多核 CPU |
| bge-reranker-large | 本地 | 精度更高 | 显存与延迟都上升 |
| Cohere rerank | 云服务 | 多语言效果好 | 数据出库，有候选数上限 |
| 大模型打分 | 云或本地 | 可解释，能按自定义标准排 | 最贵最慢 |

### 8.5 Top-K 怎么定

| 场景 | 粗排 | 精排 | 进上下文 |
|---|---|---|---|
| 有重排 | 50 左右 | 20 | 3 到 8 |
| 无重排 | 直接取 3 到 5 | — | 3 到 5 |
| 答案跨多段 | 100 | 30 | 8 到 12，需去重压缩 |

没有重排时放大 K 会直接掉准确率，因为噪声排名不分先后地挤进上下文。

### 8.6 重排救不回什么

召回阶段没捞到的，重排救不回。这是定位问题的第一原则：先看 Recall，再看排序。

多跳问题里，单条打分也不够。答案需要同时命中两段才成立，而两段各自看都不够相关。这种情况要靠查询拆分或图检索，不是加重排。

## 九、上下文组装与生成

### 9.1 组装四件事

| 事 | 做法 | 不做会怎样 |
|---|---|---|
| 排序位置 | 最重要的证据放开头或结尾 | 落在长中段的证据被忽略 |
| 体积控制 | 按预算裁剪，超出的摘要 | 挤掉系统指令，模型开始自由发挥 |
| 来源编号 | 每段带编号与出处 | 无法溯源，答案不可信 |
| 多样性 | 相似块去重，必要时用 MMR | 十条同义片段占满预算 |

### 9.2 位置效应

模型对长上下文的中段注意力最弱，开头与结尾最强，这是常说的 U 型效应。工程做法：把高分块交替放在首尾。

```python
def order(chunks):
    left, right = [], []
    for i, c in enumerate(chunks):
        if i % 2 == 0:
            left.append(c)
        else:
            right.insert(0, c)
    return left + right
```

### 9.3 MMR：去重而不掉相关性

```python
def mmr(q_vec, chunks, vecs, k=5, lam=0.5):
    picked = []
    while len(picked) < k:
        best, best_s = None, -1e9
        for c, v in zip(chunks, vecs):
            if c in picked:
                continue
            rel = cos(q_vec, v)
            div = max((cos(v, x) for x in picked), default=0)
            s = lam * rel - (1 - lam) * div
            if s > best_s:
                best, best_s = c, s
        picked.append(best)
    return picked
```

`lam` 控制相关性权重。设 1 等于不做 MMR，设 0.5 在保持相关的前提下压重复。适合「同一段话被多份文档重复」的语料。

### 9.4 上下文预算

预算要同时留给四样：系统指令、检索片段、对话历史、输出。经验比例是片段不超过一半，历史不超过四分之一，其余留指令与输出。总量逼近上限时，先压历史，再压片段，最后才动指令。

### 9.5 生成器选型

| 维度 | 口径 |
|---|---|
| 上下文长度 | 至少是注入内容的两倍，留空间给指令与历史 |
| 中文能力 | 国内部署优先国产模型，术语与语感更稳 |
| 工具调用 | 复杂流程要 Function Calling 支持 |
| 成本 | 简单问答用小模型，多跳推理才用大模型 |

### 9.6 提示词骨架

```text
[角色] 你是{领域}顾问，只依据下面资料回答。
[规则] 1 资料没有就说"资料不足"；2 每句结论后标 [编号]；
       3 不补充资料之外的事实；4 用{语言}，控制在{篇幅}。
[资料]
[1] {chunk1}
[2] {chunk2}
[问题] {question}
[回答]
```

四条规则缺一不可：第一条防幻觉，第二条保证可溯源，第三条防止模型拿记忆补，第四条控制形态。

一个容易被忽略的细节：要求模型「引用编号」时，编号必须在资料里真的存在，且格式统一。模型会引用不存在的编号，这本身是幻觉的一种。

### 9.7 拒答与召回是一对

召回不足时，守规则的模型大量拒答，用户以为系统坏了；放开规则，模型开始编。

工程上分三层：高置信度直接答；中置信度答并标注「依据有限」；低置信度明确拒答，并给出「换个问法」或「联系人工」的建议。

置信度可用三个信号合成：最高重排分数、命中块数量、命中块之间的分散程度。分数高且集中，可信；分数低且分散，多半没有答案。

### 9.8 生成侧四种优化

| 手法 | 作用 | 代价 |
|---|---|---|
| 流式输出 | 首字延迟的感知大幅缩短 | 后处理变难 |
| 答案缓存 | 高频相同问题不重复调模型 | 知识更新后要清缓存 |
| 上下文压缩 | 用小模型先压缩片段 | 压缩会丢细节，要抽查 |
| 结构化输出 | JSON 模式，便于前端与判分 | 复杂内容不好塞进结构 |

## 十、多轮对话 RAG

### 10.1 为什么单轮做法在多轮里失效

用户第二轮问「它怎么配置」，检索用的是字面的「它」，必然跑偏。问题不在检索算法，而在查询本身脱离上下文后是歧义的。

### 10.2 三条做法

| 做法 | 具体 | 代价 |
|---|---|---|
| 历史拼进查询 | 把前两轮问答拼在问题前面 | 噪声变多，长历史稀释关键词 |
| 先改写独立查询 | 让模型把问题改写成自包含的一句再检索 | 多一次模型调用，延迟上升 |
| 对话状态加槽位 | 维护已确认的实体、条件、排除项 | 要设计状态结构，边界多 |

工程默认是第二条。改写提示词只要一句：「把用户最后一句话改写成不依赖上文、可以独立理解的问题，只输出改写后的问题。」

### 10.3 对话状态该记什么

三样：用户已确认的事实（产品型号、时间范围）、当前任务的目标、已经排除的选项。前两样用于改写查询，第三样用于避免重复推荐同一批被否掉的内容。

### 10.4 历史怎么压

超过五轮就压。两种压法：滑动窗口只留最近 N 轮，简单但会丢早期信息；摘要压缩把早期对话压成一段摘要，成本高但保留要点。

优先压「用户说过的背景」，保「已确认的关键参数」。参数丢了会导致重复追问。

## 十一、评估

### 11.1 为什么要分两段评

RAG 出错有两类原因：检索没找到证据，或找到了但生成没用。不分段评，永远定位不到问题。

### 11.2 五个核心指标

| 指标 | 评的是 | 怎么算 |
|---|---|---|
| Context Precision | 召回的块里相关的比例，且是否排在前面 | 逐个判断 top-k 是否相关，越靠前权重越高 |
| Context Recall | 答案需要的信息点被覆盖多少 | 从标准答案抽信息点，逐点检查是否出现在召回里 |
| Context Relevancy | 召回内容整体是否偏题 | 模型判断召回内容与问题的相关性 |
| Faithfulness | 回答的每句是否能从资料推出 | 把回答拆成独立陈述，逐条判断可推导性 |
| Answer Relevancy | 是否直接、完整回答了问题 | 看是否覆盖问题的各维度、有无多余内容 |

### 11.3 Faithfulness 的算法细节

把回答拆成若干独立陈述，逐条问：这条能否仅从给定资料推出。能推出计数，除以总数即分数。

注意事项：拆句要按语义拆，不按标点硬拆；同一个事实换个说法算能推出；引用编号本身不算陈述。

### 11.4 RAGAs 用法

```python
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall
from datasets import Dataset

ds = Dataset.from_dict({
    "user_input": ["什么是 RAG"],
    "retrieved_contexts": [["RAG 是检索增强生成，先检索再生成"]],
    "response": ["RAG 是先检索后生成的技术"],
    "ground_truth": ["RAG 是检索增强生成技术"],
})
print(evaluate(ds, metrics=[faithfulness, answer_relevancy,
                            context_precision, context_recall]))
```

四个字段是必需：问题、召回的上下文、模型回答、标准答案。

### 11.5 四种评估方式对比

| 方式 | 要不要人工 | 优点 | 缺点 |
|---|---|---|---|
| RAGAs | 要标准答案 | 端到端可算，指标完整 | 依赖标注质量，指标本身也是模型判的 |
| LLM 当裁判 | 不要 | 可自动化，能按自定义标准评 | 有偏好，需抽检校准 |
| 人工评估 | 全要 | 金标准 | 成本高，不可持续 |
| 规则匹配 | 不要 | 客观、可重复 | 只能查精确项，评不了语义 |

### 11.6 数据集怎么造

从真实提问里抽，二十到五十条即可看方向。每条要三个字段：问题、应命中的证据来源、标准答案。

分三组：九十条常规、五到十条边界（无答案的、歧义的）、五到十条对抗（要跨段拼的）。没有无答案样本，就测不出拒答能力。

调参样例与最终测试样例必须分开，否则等于背答案。

### 11.7 持续评估

上线后按周跑同一批。改一处看一处，A/B 只换一个变量。指标掉了先看检索段，再看生成段。

## 十二、性能与成本

### 12.1 四个瓶颈，按耗时排序

| 环节 | 量级 | 优化手段 |
|---|---|---|
| 查询向量化 | 几十毫秒 | 批量、缓存、换小模型 |
| ANN 检索 | 几到几十毫秒 | 调 ef、量化、分区 |
| 重排 | 百毫秒级 | 减少候选数、换轻模型 |
| 生成 | 秒级，占大头 | 流式、缓存、压缩上下文 |

绝大多数「RAG 很慢」的报告，瓶颈在生成而不在检索。先测再优化。

### 12.2 检索侧优化

| 手段 | 作用 | 代价 |
|---|---|---|
| HNSW 调参 | 精度与延迟平衡 | 改了要重建索引 |
| 批量 Embedding | 吞吐提升 | 首字延迟变高 |
| 向量量化 | 内存降、速度升 | 精度略降 |
| Embedding 缓存 | 重复查询不重算 | 要管理失效 |
| 查询改写 | 召回率上升 | 多一次模型调用 |

### 12.3 生成侧优化

流式输出改善的是感知延迟，不改变总耗时。答案缓存对高频重复问题有效，但要随知识更新清空。上下文压缩能显著降 token，代价是可能丢细节。模型蒸馏降成本，但要重新评测。

### 12.4 成本估算口径

一次问答的成本由四块构成：查询 Embedding、检索与重排的算力、注入的 token 数、生成的 token 数。前两块通常可忽略，后两块是大头。

降本顺序：先把注入块数从十降到五；再把生成模型换成小模型试效果；最后才考虑缓存与蒸馏。

## 十三、高级形态与检索范式

### 13.1 五种增强

| 形态 | 改进 | 适合 | 复杂度 |
|---|---|---|---|
| HyDE | 生成假设答案辅助检索 | 问法与原文差距大 | 低 |
| Self-RAG | 模型自己决定检索不检索、结果够不够 | 检索成本敏感 | 中 |
| LongRAG | 大块 4K 到 8K、重叠 20% 到 30%，检索完整段落 | 长文档理解 | 中 |
| GraphRAG | 抽实体关系建图，社区摘要支持全局问答 | 多跳、全局归纳 | 高 |
| 多模态 RAG | 文本、图像、音频统一检索 | 图文混排文档 | 高 |
| Agentic RAG | 检索变成工具，由 Agent 规划多轮 | 复杂多跳问答 | 最高 |

### 13.2 Self-RAG 的标签机制

让模型给每句话打标签：要不要检索、检索结果相关不相关、结论被支持还是矛盾。

```text
[Retrieval] 需要外部知识验证
[No Retrieval] 可直接回答
[Relevant] 检索结果高度相关
[Irrelevant] 检索结果不相关
[Supported] 回答被资料支持
[Contradict] 回答与资料矛盾
```

收益是少做无用检索；代价是多轮判断，延迟上升，且标签本身也会判错。

### 13.3 GraphRAG 两阶段

构建期：源文档 → 实体识别 → 关系抽取 → 建图 → 社区检测 → 为每个社区写摘要。查询期：局部问题走实体邻域检索；全局问题汇总社区摘要逐层归并。

它能回答「这批材料主要讨论什么」这类问题，因为摘要本身就是全局视图。代价是建图最贵，抽取错误会沿边扩散，比错片段更难发现。

### 13.4 六种形态对照：一条轴、四个范式、两个补丁

六者的分歧可以压到一条轴上：**理解的时点放在写入端还是查询端**。写入端＝入库时把理解做完，查询时直接读；查询端＝入库只存原文，查询时现算。每往写入端移一格，查询便宜一分，错误被固化一分，语料变更后的重建成本涨一分。这条轴比「谁更先进」有用，因为它直接对应你愿意在哪一端犯错。

| 形态 | 理解的时点 | 检索单元 | 强在哪 | 主要失效 |
|---|---|---|---|---|
| 向量 RAG | 查询端 | 片段 | 海量文档的局部事实 | 相似不等于完整 |
| Contextual Retrieval | 查询端（索引时补块） | 片段 + 位置说明 | 块里缺主语时召回明显改善 | 一次性 token 成本，依赖 prompt caching |
| GraphRAG | 写入端（预计算摘要） | 关系 | 多跳追查、全局归纳 | 抽取错误沿边扩散，语料必须静态 |
| LightRAG | 写入端（动态增量） | 关系 + 向量 | 增量维护、宏观归纳便宜 | 结论随关键词漂，首建不便宜 |
| 文档树导航 | 索引端（结构先行） | 章节 | 长文档跨章节取证 | 只认结构清晰的文档 |
| LLM-Wiki | 写入端（理解全部前置） | 概念页 | 知识复用与累积 | 规模化维护，目录有物理上限 |

它们不在同一层：RAG 与两条图路线是检索结构，文档树是文档内部的导航结构，LLM-Wiki 是知识的组织形态，Contextual Retrieval 是挂在向量 RAG 上的一个索引期补丁。所以不是六选一，是按任务路由。

还有一类不在这张表里：**OpenViking 这类上下文系统换了一层**——知识库降格成它 `resources/` 一个目录，记忆与技能各自一个目录，见 13.13。

下面各节把三条非向量路线、两个补丁与成本口径展开写清，判断取舍见知识库同名文档的「检索范式」节。

### 13.5 GraphRAG 怎么做

构建分两段。第一段抽实体与关系：模型读文本，输出实体表与关系表，同名实体要合并。第二段做社区检测：把关系紧密的节点聚成群，为每个群写一段摘要。

检索分两条路。局部检索面向具体问题：先用向量或关键词定位实体，再沿边扩一跳两跳，把邻居与原文一起带进上下文。全局检索面向归纳性问题：不找具体实体，而是汇总社区摘要逐层归并，回答「这批材料主要讨论什么」。

四个工程难点。

| 难点 | 表现 | 处理 |
|---|---|---|
| 抽取错误 | 错抽的关系留在图里，沿边扩散 | 抽取模型要强，抽样人工核验 |
| 同义消歧 | 一个设备型号五六种写法 | 建别名表，入库前归一 |
| 原文映射 | 图节点找不到出处 | 每个节点存原文位置 |
| 增量更新 | 社区划分会变，摘要要重算 | 按批更新，不逐条改 |

代价一句话：错误的关系比错误的片段更难发现，因为没有哪一段原文能拿来对质。

实现：microsoft/graphrag 是官方实现，抽取、社区识别、局部与全局检索齐全；HKUDS/LightRAG 走图与向量融合，支持增量维护，工程门槛更低。

### 13.6 文档树导航

向量与图在一种问法上会同时失效：「配置了单点登录，部分用户仍无法登录，这与权限设置或版本有关吗」。答案散在配置说明、权限设置、版本限制、常见问题四章里，相隔几十页。只召回最相似的段落，前置条件与依赖关系全漏。

做法：解析文档，按目录、标题层级或版式建树，节点与页码或正文范围关联，按需为节点生成摘要。查询时模型先看树选章节，调读取工具取原文，读完判断不够再要一章。

节点不存内容，只存三件事：这一节讲什么、上下层是谁、去哪读。检索是模型主导的多步阅读，不是一次召回。

同一条思路的极简版是不建树：给模型一份写好的 `llms.txt` 目录，配 grep 一类工具，让它在文件系统里自己翻。编码智能体的成功让这条「推理驱动检索」的路重新被重视。

局限：只适合章节清晰的长文档（年报、合同、手册、接口文档）；多步阅读延迟高、token 花得多；建树与摘要同样会出错；扫描件要先解决解析与 OCR，否则树本身就是错的。所以它通常当副手，不当唯一通道。

实现：VectifyAI/PageIndex，MIT，自述 vectorless、reasoning-based，不用向量库、不做 embedding、不切块。

### 13.7 LLM-Wiki 三层与三动作

核心主张：不要让模型每次查询时从原始文档重新检索，而是把知识编译成一套持久、互链的页面，并持续维护。RAG 像解释器，每次现算；Wiki 像编译器，编译一次产出可复用的产物。

三层结构。

| 层 | 装什么 | 谁维护 |
|---|---|---|
| raw | 原始资料：文章、论文、图片、数据，只读 | 人 |
| wiki | 概念页、实体页、对比页，页间交叉链接，保留来源回链 | 模型 |
| schema | 命名、分层、更新与回写规则，通常就是一个 Markdown 文件 | 人写，模型遵守 |

三个动作：ingest 把新资料转成对页面的修改，一篇新文档往往改动十几页；query 回答时走 wiki 不走原文，有价值的回答回写成新页；lint 定期查过时内容、冲突结论、孤立页面、缺失链接。

读取不靠相似度，靠结构：先读索引页，再进相关概念页，需要时沿链接延伸。加载顺序可以直接写进 `AGENTS.md` 或技能文件，等于把检索策略变成可版本化的规则。

规模化难点：页面上千后，源一变就要定位受影响页面、处理冲突与错误，时间与 token 成本都不低；工程上还要解决并发写入、版本回滚与权限继承。

实践口径：先把反复使用、相对稳定的核心知识编成 Wiki（业务术语、指标口径、操作规程、编程上下文），海量低频内容等发现复用价值再整理。

### 13.8 融合四条路与治理代价

| 路径 | 做法 | 收益 | 代价 |
|---|---|---|---|
| 向量找入口，图做扩展 | 先定位实体或片段，再沿有来源的关系扩一两跳 | 多跳问题有依据 | 要限关系类型与跳数，否则远亲近邻全塞进上下文 |
| 向量定位文档，树导航深读 | 先检索候选文档，短文档读全文，长文档交给树 | 长文档不漏前置条件 | 要用元数据对齐文档身份与版本，避免检索到旧版、读到新版 |
| 按知识稳定性分工 | 核心稳定知识编 Wiki，复杂长文档建树，长尾走 RAG | 各用所长 | 要路由，路由错就等于白建 |
| Wiki 反哺其他模式 | 用整理好的 Wiki 当 RAG 与图抽取的输入 | 分块与召回质量都上升 | 要先有维护成本 |

第四条最容易被忽略，但收益最快：拿整理过的 Markdown 建向量库，效果明显好于拿原始 PDF。

治理代价是融合方案里最容易被低估的一项。同一条知识在片段、图节点、文档树、Wiki 页里各存一份，源内容或权限一改，四处都要同步失效。很多方案停在演示阶段，就是卡在这里。

| 项目 | 形态 | 说明 |

| microsoft/graphrag | 图增强 | 实体关系抽取、社区识别、局部与全局检索 |
| HKUDS/LightRAG | 图加向量 | 融合检索，支持增量维护 |

标准化格式：Google Cloud 2026-06-12 发布的 Open Knowledge Format v0.1，把这类形态定义成一个装 Markdown 的目录，每页顶部是 YAML 元数据，页间用链接表达关系。目标是任何人不需 SDK 就能产出，任何系统不需集成就能消费。

### 13.10 Contextual Retrieval：索引时补「这个块是谁」

问题出在切块那一刻，不在检索那一刻。一个块里写着「公司营收环比增长 3%」，哪家公司、哪个季度块里没有。嵌入算出的坐标里没有公司名，只会往「增长/季度」这类泛化语义靠；字面检索也匹配不到，因为公司名不在这一块里。**这是索引期丢的信息，检索期再怎么调权重也补不回来。**

做法：索引时让 LLM 给每个块写一段 50–100 token 的位置说明（这份文档叫什么、属于哪一章、这一段在讲谁的什么事），拼在块前再建索引。位置说明本身可以用 prompt caching 复用，避免每次重算文档级上下文。

Anthropic 2024-09-19 的实测口径（top-20 块检索失败率）：

| 做法 | 失败率 | 相对基线降幅 |
|---|---|---|
| 基线（普通向量检索） | 5.7% | — |
| 加上下文的位置说明 | 3.7% | 35% |
| 再加一路上下文 BM25 | 2.9% | 49% |
| 再加一轮 rerank | 1.9% | 67% |

一次性成本 $1.02 / 百万 document token，且必须靠 prompt caching 才成立。报数字时要说清 1.9% 是三者齐上，不是单靠位置说明。

工程要点四条：

- 位置说明要短，超过 100 token 就吃掉收益；内容只要「文档标题 + 所在章节 + 这段讲谁」。
- 说明质量取决于喂给模型的文档级上下文，整份文档塞不进窗口时用摘要替代，效果会掉。
- 官方测的是英文语料，中文要重测；中文的成本差异主要在分词后的 token 数上。
- 它补的是「块自己是谁」，补不了「块与块的关系」——关系问题仍然要走图（13.5）。

失效边界：块本身信息完整时几乎无增量；说明写错会把错误固化进索引，且下游看不出来。

### 13.11 LightRAG：把 GraphRAG 的更新病改成并集

它针对的不是 RAG 的老问题，是 GraphRAG 自己造成的问题。图建好之后新数据一进来，社区划分就变，原来那批摘要整批作废。论文给的口径：进来一份同规模新数据，重建约 **1,399 万 token**（1,399 个社区 × 2 遍拆旧建新 × 每份约 5,000 token）。

LightRAG 的处理是把新抽出的节点集、边集直接与旧的取**并集**，是 INSERT 而不是 DROP TABLE 重建。检索走两路：主题词一路、实体词一路，两路各自打图再合并。所以它的宏观能力来源与 GraphRAG 相反——GraphRAG 靠索引时预写的摘要（静态、稳定、贵），LightRAG 靠查询时把问题拆成关键词打图（动态、便宜，代价是结论随关键词漂）。

三条必须知道的事实：

- **首建不便宜。** 同样要逐块调 LLM 抽实体，量级与 GraphRAG 的抽取阶段相当。省下的是检索（<100 token、一次调用）与增量，不是建库。
- **对 GraphRAG 只是几乎打平。** 论文 Overall 胜率四个领域 54.8% / 52.0% / 52.8% / **49.6%**，第四个领域是输的。中文圈流传的「全面超越」翻到原表第四个数就站不住。
- **增量不等于免费。** 并集会让图越来越稠，社区边界逐渐模糊，要定期做一次合并与剪枝，否则检索时邻居越捞越多。

还有一条容易漏的：真把索引成本降到近零的是 LazyGraphRAG，但它没进开源库，pip 装不到。所以工程上仍按 LightRAG 这一档估成本。

### 13.12 成本与门限：三个能直接说出口的数

| 口径 | 数值 | 含义 |
|---|---|---|
| 不做 RAG 的门槛 | 知识库 < 200,000 token（约 500 页） | 整库塞进上下文即可，Anthropic 官方口径。先数页数，再谈方案 |
| GraphRAG 建图 | 600 token 窗口、约 100 万 token 语料（1,669 个块）、16GB 虚拟机 → 281 分钟 | 换语料要重测，只能拿来做量级估算：每分钟约 3,600 token 的抽取吞吐 |
| GraphRAG 全局查询 | 20 秒起，单次读几十万 token、几百次调用 | 它只对「把全文塞进上下文」省钱，对向量检索是纯增量 |

另外两个上限值得记住：LLM-Wiki 的检索索引就是 `index.md`，204 页时目录已 2.8 万 token，再往上导航退化成猜；它的查询 token 在一篇语料仅 24 篇的预注册实验里测出是 RAG 的 21 倍。

**成本估算的正确姿势**：按抽取 token 量乘你的模型单价，先算建库一遍的账，再乘预计重建次数。GraphRAG 这类方案的账几乎全部落在「重建」上，不在「查询」上。

### 13.13 OpenViking：换一层，不是第六条路线

火山引擎开源，在 `viking://` 下开一棵虚拟文件系统：`resources/` 放文档与代码（也就是你说的知识库）、`memories/` 放偏好与经验、`skills/` 放怎么做任务。每个目录自动生成两层摘要（L0 一句话、L1 结构与要点），原文算第三层，按需才读。检索不扫扁平索引，先靠一次意图分析定位目录或子树，再往下钻。

它的意义不在性能，在决策前提：如果真实问题是「Agent 的上下文怎么管」，前面所有检索方案在这个系统里都退格成 `resources/` 一个目录里的选项。这时该选的是上下文系统，不是检索方案。

代价：AGPL-3.0（商用分发要过法务）、要独立起服务、依赖嵌入与视觉模型提供方、官方未公开十万级文件下的延迟与成本；LoCoMo 上自报的记忆准确率提升（三套 Agent 从 24.2% / 33.4% / 57.2% 提到 80–83%）是自家模型组合跑的，无第三方复现。仓库实测 41,984★、未归档（2026-11-11）。

### 13.14 Ontology：语义层与执行层

前面所有小节都在回答「怎样取证」。这一节换一层：**业务对象怎样表达、允许怎样改变**。三者可以叠在一个系统里，但不是同一条演进线的三代。

| 能力 | 主要问题 | 成本与边界 |
|---|---|---|
| 普通 RAG | 从资料里找依据，给生成补上下文 | 召回、解析、更新、权限都要维护；向量检索只是其中一条实现路线 |
| GraphRAG | 从语料抽图、生成社区摘要，用关系与汇总结构增强查询 | 建图、消歧、更新有成本；图上有关联不保证业务结论正确，官方自己也保留普通检索路径 |
| Ontology | 把已集成的数据组织成业务对象、关系与受控操作 | 要维护数据映射、业务逻辑、权限与执行集成，是业务与数据治理投入 |

**通用本体与运营本体要分开讲**。[W3C OWL 2](https://www.w3.org/TR/owl2-overview/) 定义类、属性、个体与形式语义，给的是建模能力，推不出审批、审计或业务系统回写。[Palantir Ontology](https://www.palantir.com/docs/foundry/ontology/overview/) 是产品层面的定义，建立在已集成的数据集、虚拟表与模型之上，分两块：

- **语义部分**：对象、属性与关系，统一「这是什么、与什么有关」。
- **执行部分**：Action Types、Functions 承接业务操作与计算逻辑，配合平台权限、应用限制与治理。

一项业务动作能否执行，取决于四件事同时成立：定义了规则、绑定了实现、配置了权限、底层系统支持。只把对象命名清楚，一步都没到。

**两类 MCP 面向的人和权限不同**（这是最容易混的一处）：

| 官方入口 | 面向谁 | 能力与边界 |
|---|---|---|
| [Ontology MCP](https://www.palantir.com/docs/foundry/ontology-mcp/overview/) | 业务使用者与消费业务能力的 Agent | 把应用的 Object Types、Action Types、Query Functions 暴露为 MCP tools；可读对象、执行预定义 Action、运行查询，受应用限制约束 |
| [Palantir MCP](https://www.palantir.com/docs/foundry/palantir-mcp/overview/) | 构建本体与应用的开发者、编码 Agent | 可修改本体类型、开发应用、操作数据集与转换；官方明确它**不能写入实际 Ontology 业务对象数据** |

「允许修改本体结构」与「允许执行业务动作」必须分别授权。MCP 只提供调用接口，权限与业务约束仍由服务及平台落实。两份官方概览能证明能力存在，但**未给出明确 GA 日期**，所以不要引用「某年正式 GA」这类表述。

**落到一个具体项目，先查三件事**（不等同于要上独立本体层）：

1. 同一个对象在不同系统里能否对齐身份，指标口径有没有统一来源。
2. 每个写操作是否明确参数、状态前提、权限与返回结果，而不是给模型一个任意改表入口。
3. 操作是否有审批条件、幂等处理、失败恢复与审计，能否从执行结果验证状态变化。

这三项在已有领域模型与业务服务里就能落实。要不要加独立本体层，由跨系统语义复用与治理需求决定，不由「别人都在讲 Ontology」决定。

## 十四、生产化

### 14.1 部署形态

索引与查询分离。索引走批处理，可离线、可重跑；查询走在线服务，要低延迟、可扩容。两者共用一个向量库，但读写权限不同。

### 14.2 可靠性四条

| 场景 | 做法 |
|---|---|
| 检索服务挂了 | 降级为纯生成，并明确告知没有引用 |
| 重排超时 | 跳过精排，直接用粗排结果 |
| 库正在重建 | 双版本并行，切流量而不是停机 |
| 答案被质疑 | 用 trace 回查当时召回了哪些块 |

### 14.3 监控四条曲线

检索命中率、拒答率、首字延迟、单次 token 消耗。四条同时看：命中率跌而拒答率涨，说明召回坏了；命中率正常但拒答率涨，说明提示词或阈值改坏了。

### 14.4 上线清单

- 解析结果抽查过表格与跨页段落
- 分块参数按文档类型分组
- 每块带来源、页码与权限元数据
- 提示词里有「只依据资料」与拒答规则
- 评估集已建，改动前后跑同一批
- 有 trace，能回查每次召回了什么
- 有降级路径，检索不可用时不至于整站挂掉

## 十五、安全与隐私

### 15.1 四道边界

| 威胁 | 场景 | 做法 |
|---|---|---|
| 库内内容含指令 | 文档里写着「忽略之前的指令」 | 片段一律当数据，只进资料区，不进系统指令区 |
| 用户输入注入 | 用户直接要求越权 | 分隔标记加声明，规则冲突以系统侧为准 |
| 越权检索 | 低权限用户问到高权限文档 | 元数据带权限字段，先过滤再检索 |
| 敏感信息外泄 | 答案里带出手机号、身份证 | 输出侧脱敏，日志不记原文 |

### 15.2 脱敏

```python
PATTERNS = [(r"\b\d{11}\b", "[手机号]"),
            (r"\b\d{18}\b", "[身份证]"),
            (r"\b[\w.-]+@[\w.-]+\.\w+\b", "[邮箱]")]
def mask(text):
    for p, r in PATTERNS:
        text = re.sub(p, r, text)
    return text
```

脱敏放在两处：入库前脱敏一次，输出前再脱敏一次。只做一处，换个入口就漏。

### 15.3 审计

记录五件事：谁问的、问了什么、召回了哪些文档、答案是什么、耗时多少。审计日志本身也要脱敏，否则变成新的泄露源。

## 十六、常见误区与排查

### 16.1 五个误区

| 误区 | 实际 |
|---|---|
| Embedding 越大越好 | 领域失配比维度不足更常见，先看语料再换模型 |
| top_k 越大越好 | 没有重排时放大 K 直接掉准确率 |
| 全库一种切分 | 合同、代码、网页的最优切法完全不同 |
| 只优化检索 | 提示词缺约束时，检索再好也会被模型丢一边 |
| 向量库能替代关系库 | 向量库只解决相似性，事务与精确查询仍要关系库 |

### 16.2 排查顺序

先看检索有没有捞到证据，再看生成有没有用证据，最后看组装有没有把证据挤掉。顺序反了，会在提示词上反复调，问题其实在切分。

### 16.3 症状对照

| 症状 | 先查什么 |
|---|---|
| 答非所问 | 召回块是否相关；不相关就是切分或 Embedding |
| 说资料不足但其实有 | 阈值过高、top_k 过小、同义改写未覆盖 |
| 答案有编造 | 提示词缺「只依据资料」，或资料里有相似但错误的内容 |
| 前后矛盾 | 同一事实在库里有两个版本，旧版没删 |
| 慢 | 先看生成阶段，再看重排候选数 |

## 十七、框架怎么选

产品与框架手册在 [[02-AI/AI专项/AgentHarness/框架手册/README|AgentHarness/框架手册]]，这里只给判断。

| 框架 | 定位 | 什么时候用 | 代价 |
|---|---|---|---|
| LangChain | 通用编排，组件最全 | 要自己组装流水线、后续接 Agent | 抽象层多，出问题要读源码 |
| LlamaIndex | 以数据与索引为中心 | RAG 是主任务、要多种索引 | 生态比 LangChain 小 |
| Dify | 可视化编排加知识库 | 快速交付、少写代码 | 深度定制受限 |
| RAGFlow | 开源 RAG 引擎，解析强 | 文档解析是主要痛点 | 资源占用高 |
| Haystack | 组件化管道 | 要可控的生产级管道 | 上手慢 |
| MaxKB、FastGPT 一类 | 成品知识库平台 | 只要一个能用的问答站 | 二次开发边界窄 |

选型口诀：学习与做对照选 LangChain 或 LlamaIndex，每一步都能换；交付选 Dify 或 MaxKB；解析难就上 RAGFlow。换框架不改原理，只改写代码的方式。

## 十八、实验结论

状态：未跑。方向池 D04 到 D07 都落在这里。

| 方向 | 基线 | 增强 | 主指标 |
|---|---|---|---|
| D04 混合召回 | 单路向量 | 向量加 BM25，RRF 融合 | 固定 top-k 的 Recall@k，分精确词与语义改写统计 |
| D05 检索重排 | 同一批候选的原始排序 | 加重排，输出条数不变 | nDCG@k、证据命中率、额外时延 |
| D06 结构切分 | 固定长度切分 | 标题与段落感知切分 | 证据完整率、引用定位正确率、索引体积 |
| D07 图谱辅助 | 向量召回 | 用给定小图谱扩展相邻实体 | 多跳问题证据覆盖率、无关扩展比例 |

共同口径：固定测试集与模型版本，每轮只切一个变量，收益与代价一起记。混合检索的四组对照口径已写在 7.10，可直接用。
