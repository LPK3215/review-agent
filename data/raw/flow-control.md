## 一、这一层管什么

### 1.1 Agent 与普通程序的可靠性差异

| 维度 | 普通服务 | Agent |
|---|---|---|
| 单次执行 | 毫秒到秒，可重试 | 秒到小时，重试代价高 |
| 失败原因 | 多是确定性的（空指针、超时） | 还有模型判断错、工具选错 |
| 状态 | 无状态，重启即恢复 | 有状态，重启要接上 |
| 中途干预 | 只能重启 | 可以在任意步骤停下等人 |
| 副作用 | 事务保证 | 调外部系统，事务管不到 |

结论：普通服务靠「重试 + 事务」，Agent 还要多一层「可中断、可恢复、副作用可重放」。

### 1.2 四类失败

| 类型 | 例子 | 能不能自动重试 |
|---|---|---|
| 瞬时故障 | 网络抖动、下游 429、超时 | 能，退避重试 |
| 永久故障 | 参数非法、鉴权失败、资源不存在 | 不能，重试只是浪费 |
| 语义故障 | 工具选错、参数指向错对象 | 不能自动，要改判断 |
| 编排故障 | 节点卡死、循环不收敛、状态不一致 | 要超时与步数上限兜底 |

只有第一类值得重试。把其余三类也丢进重试，结果是延迟放大、账单上升、问题依旧。

### 1.3 三道防线

```text
预防（执行前）→ 检测（执行中）→ 恢复（失败后）
```

三条同时存在才叫可靠。只有预防，等于赌不会出事；只有恢复，等于每次都重跑。

## 二、六种编排模式

### 2.1 总表

| 模式 | 结构 | 适合 | 代价 |
|---|---|---|---|
| 链式 | A → B → C 固定顺序 | 步骤确定的流水线 | 一步错全链停 |
| 路由 | 先分类，再分发到不同分支 | 输入类型差异大 | 分类错就全错 |
| 并行 | 多个子任务同时跑，最后汇总 | 子任务互不依赖 | 汇总要处理冲突 |
| 协调者/工作者 | 一个调度者拆任务，多个执行者干 | 任务可拆且异构 | 调度者是瓶颈 |
| 评估者/优化者 | 生成 → 评审 → 再生成 | 质量要求高、可迭代 | 轮数与成本翻倍 |
| 自主循环 | Agent 自己决定下一步 | 开放任务 | 不可预测，要步数上限 |

### 2.2 链式

```python
def pipeline(text):
    step1 = llm(f"翻译成英文：{text}")
    step2 = llm(f"总结要点：{step1}")
    return llm(f"改写成三条推文：{step2}")
```

要点：每步的输入输出格式固定；中间产物落盘，便于单步重跑；链路超过五步就要考虑并行或拆分。

### 2.3 路由

先判断输入属于哪一类，再走对应分支。分类用规则还是模型，取决于类别是否可枚举。

规则分类便宜且确定，但覆盖不了新类型；模型分类能泛化，但有误判且要成本。生产上常见做法是规则先挡一层，剩下的交给模型。

### 2.4 并行

适用于子任务互相独立。三种并行：分支并行（同一输入走多条路）、分片并行（把大输入切片）、竞争并行（多方案取最优）。

```python
results = await asyncio.gather(*[worker(chunk) for chunk in chunks])
merged = merge(results)
```

合并阶段是真正的难点：结果顺序、重复内容、冲突结论，都要显式处理。

### 2.5 协调者/工作者

```text
协调者：拆任务 → 分配 → 收结果 → 汇总
工作者：接到子任务 → 执行 → 返回
```

适用研究与写作这类「可拆分且子任务差异大」的任务。协调者本身是瓶颈：拆分质量决定上限，它不知道该拆什么时，工作者再多也没用。

代价是 token 与延迟随工作者数量线性增长，要设置上限。

### 2.6 评估者/优化者

```text
生成 → 评审（按明确标准打分并指出问题）→ 按意见重写 → 再评审
```

关键是评审标准要写死，否则每轮意见都不同，模型无法收敛。轮数设上限（常见 2 到 3 轮），超过后收益迅速递减。

### 2.7 自主循环

Agent 自己决定调用什么工具、循环几次。能力最强，最不可控。

三条必须有的约束：最大步数、单步超时、总成本上限。缺一条就可能烧穿额度。

### 2.8 怎么选

```text
步骤固定？ ── 是 ── 有分支？ ── 否 → 链式
                          └─ 是 → 路由
          └─ 否 ── 任务可拆？ ── 是 → 协调者/工作者（或并行）
                             └─ 否 ── 质量要求高？ ── 是 → 评估者/优化者
                                                └─ 否 → 自主循环
```

## 三、错误分类与三层策略

### 3.1 三类错误

| 类别 | 表现 | 处理 |
|---|---|---|
| 输入错误 | 缺字段、类型错、超长、注入 | 入口校验，直接拒绝 |
| 处理错误 | 模型输出不合法、工具返回异常、超时 | 重试、降级、改道 |
| 输出错误 | 格式不符、内容违规、引用错误 | 后置校验，拦截或重写 |

分类的意义是定位：入口错误不该进重试，输出错误不该在模型侧调参数。

### 3.2 预防

- 输入校验：必填、类型、长度、枚举。
- 工具白名单：不在清单里的工具模型看不到。
- 提示词约束：输出格式写死，并给合法示例。
- 预算约束：单次调用的最大 token、最大步数。

### 3.3 检测

- 结构校验：JSON 能否解析、字段是否齐全。
- 结果合理性：空结果、全零、明显异常值。
- 耗时监控：单步超过阈值即告警。
- 循环检测：同一工具同参数重复调用。

### 3.4 恢复

| 手段 | 适用 | 代价 |
|---|---|---|
| 重试 | 瞬时故障 | 延迟放大 |
| 降级 | 依赖不可用 | 结果质量下降 |
| 换路 | 主路径失败但有备选 | 要准备备选路径 |
| 人工接管 | 决策类失败 | 依赖人力 |
| 回滚 | 已产生副作用 | 要能撤回 |

### 3.5 三种容错机制

| 机制 | 做什么 | 例子 |
|---|---|---|
| 冗余 | 关键路径有备份 | 两个模型供应商、双区域 |
| 隔离 | 故障不扩散 | 单个工具失败不拖垮整轮 |
| 监控 | 早发现 | 成功率、延迟、错误类型分布 |

## 四、超时、重试、熔断、降级

### 4.1 四种手段的分工

| 手段 | 解决 | 不解决 |
|---|---|---|
| 超时 | 无限等待 | 慢但最终成功的情况 |
| 重试 | 瞬时故障 | 永久故障，会放大损失 |
| 熔断 | 持续失败还继续打 | 已经失败的这一次 |
| 降级 | 依赖不可用 | 降级后的质量损失 |

### 4.2 框架原生件

LangGraph 1.2 之后把这几样做进了框架。

| 能力 | 归属 | 用法 |
|---|---|---|
| `RetryPolicy(retry_on=..., max_attempts=...)` | 原生 | 挂 `add_node`，只重试指定异常 |
| `TimeoutPolicy(idle_timeout=..., run_timeout=...)` | 原生 | 超时抛 `NodeTimeoutError` |
| `runtime.heartbeat()` | 原生 | 长任务续命，避免被误判超时 |
| `error_handler`（1.2+） | 原生 | 重试耗尽后做补偿路由，可 `Command(goto=...)` |
| `set_node_defaults`（1.2+） | 原生 | 图级统一 retry / timeout / error_handler |

关键一条：`interrupt()` 走 `GraphBubbleUp`，**不交给 error_handler，也不会被重试**。所以「中断」与「报错」在框架里是两条路，不会互相吞。

### 4.3 重试的三条纪律

- 只对可恢复异常重试。参数错、鉴权错重试一百次结果一样。
- 次数设上限，间隔递增（指数退避加抖动）。
- 重试前先判断幂等，非幂等操作不能盲目重试。

### 4.4 熔断

连续失败到阈值就快速失败，隔一段时间放一个探针试探。没有熔断，下游挂了会把上游的连接池与线程池一起拖死。

### 4.5 降级

三种降级方向：换成更小的模型、跳过非关键步骤、返回缓存结果。降级必须显式告知，否则用户以为拿到的是完整结果。

## 五、幂等：重试与恢复的前提

### 5.1 为什么必须有

两类场景都会导致「同一逻辑执行两次」：超时后的重试、恢复时的节点重入。没有幂等，就变成重复扣款、重复发消息。

### 5.2 三种做法

| 做法 | 机制 | 适合 |
|---|---|---|
| 幂等键 | 每次请求带唯一键，下游按键去重 | 调外部写接口 |
| 先查后写 | 存在则跳过 | 有天然业务唯一键 |
| 状态机 | 只允许从某态迁到某态，重复执行无副作用 | 长流程 |

### 5.3 落位原则

高风险动作放在「确认之后」，低风险查询放在「确认之前」。查询重跑一次无害，扣款重跑一次就是事故。

## 六、检查点

### 6.1 三个概念先钉死

| 概念 | 是什么 | 不是什么 |
|---|---|---|
| `interrupt()` | 节点内显式的业务断点，payload 要能 JSON 序列化 | 不是异常处理，不是通用暂停 |
| Checkpointer | 状态快照底座，`compile(checkpointer=...)` 才生效 | 不是默认开启 |
| `thread_id` | 检查点主键，复用即续同一条线 | 不是操作系统线程 ID |

不传 checkpointer，interrupt 无处落盘，恢复与记忆全部失效。

### 6.2 粒度是 super-step

一个 super-step 是图的一次 tick：这一步里被调度的节点（可能并行）全部跑完，才写一份完整快照。

顺序图 `START → A → B → END` 会写四份：起始、A、B、结束。看起来像节点边界，本质是 super-step 边界；并行节点在同一步里只产出一份。

### 6.3 pending writes

super-step 内部，每个节点跑完先把写入落到 task 级，不等整步结束。作用是故障恢复：同一步里 A 成功、B 失败，恢复时 A 不重跑，只补 B。

这条纠正了一个常见误解：检查点之间崩了并非全丢，丢的只是失败节点自己那部分。

### 6.4 durability 三档

| 模式 | 何时写 | 崩溃代价 | 适用 |
|---|---|---|---|
| `exit` | 只在退出时 | 中间态全无 | 长任务、性能优先、可重跑 |
| `async`（默认） | 下一步执行期间异步写 | 小概率丢最近一步 | 绝大多数场景 |
| `sync` | 下一步开始前同步写完 | 每步都有 | 钱、库存、不可重放的外部调用 |

「中途崩溃不会自动快照」只在 `exit` 下成立。默认 `async` 是有快照的，只是可能少最后一步。

### 6.5 存储四档

| 实现 | 场景 |
|---|---|
| `InMemorySaver` | 开发测试，重启即丢 |
| `SqliteSaver` | 本地单机验证 |
| `PostgresSaver` | 生产默认，多进程共享 |
| `MongoDBSaver` / Cosmos | 已有对应基础设施 |

生产上要的是「多个执行进程能访问同一份存储」，不是「用了 checkpointer」这句话本身。

## 七、四类「停下」

| # | 场景 | 谁触发 | 有没有检查点 | 怎么继续 |
|---|---|---|---|---|
| ① | 预设人工断点 | 代码里的 `interrupt()` | 有，无限期等待 | resume 加同一 `thread_id` |
| ② | 正常流转 | 运行时 | 每个 super-step 都有 | 不需要 |
| ③ | 外部取消 / 停机 | 信号、运维 | 硬杀没有；协作式 drain 有 | drain 后可续，SIGKILL 不可 |
| ④ | 异常 / 报错 | 代码或依赖 | 有上一份 | 从上一份重跑失败那一步 |

### 7.1 只有第一种是「等人」

`interrupt()` 是计划内的业务断点，不是故障。触发后保存状态、本次执行终止、无限期等待。恢复必须同一个 `thread_id`，换了就是另开一条空线程。

### 7.2 外部停机有两种

- 硬杀（`kill -9`）：进程直接没，来不及写任何东西，默认 async 下最多剩上一步的检查点。
- 协作式收尾：有原生 drain，执行时传 `RunControl()`，另起线程调 `request_drain()`，运行时在当前 super-step 跑完后停下、写检查点、抛 `GraphDrained`，之后可从这份检查点续跑。面向滚动发布与 `SIGTERM`。

drain 不是 HITL。它是「有序地停」，不是「停下来等人回话」。

### 7.3 异常不会自动变人工

普通异常默认不会变成中断，也不会弹窗等人。未捕获就冒泡终止，状态停在上一份检查点。

1.2 的 `error_handler` 是「重试耗尽后的补偿路由」，做的是处理，不是停下来等人。

一句话分界：**框架负责停在哪、存什么、从哪续；业务负责要不要停、停了问谁、续了会不会重复扣钱。**

## 八、interrupt 的四条硬规则

### 8.1 规则一：不要用 try/except 包它

它靠抛异常实现（`GraphInterrupt` 继承 `GraphBubbleUp`），被 `except Exception` 接住就再也传不回图，表现为「图卡住不动」。

正确写法：interrupt 单独一行，容易出错的代码放另一个 try，且只捕具体异常类型。

### 8.2 规则二：同一节点多个 interrupt 顺序不能改

恢复值是任务级的列表，按下标严格匹配。顺序一变、条件跳过一个、用不确定的循环，第一个就会吃掉本该给第二个的值。

并行分支同时挂起是另一套：按 interrupt ID 映射，一次性恢复。

### 8.3 规则三：payload 要简单可序列化

别塞自定义对象、别塞大块二进制。审批要用的信息（做什么、影响什么、能不能撤回）放进去，其余用 ID 引用。

### 8.4 规则四：interrupt 之前的副作用必须幂等

因为恢复是重入整个节点。高风险动作放到 interrupt 之后。

### 8.5 「出错后问人」的正确写法

```text
执行节点：try 干活 → except 具体异常 → 把错误写进 state.error
   ↓ 条件边
确认节点：state 里有 error 才 interrupt({"error": ..., "retry": ...})
```

不要在 `except` 块里直接 `interrupt()`。当前能跑，但下一次改动很容易把它挪进 try，事故就来了。

### 8.6 完整链路

```python
def approval_node(state):
    decision = interrupt({"msg": "请审批", "value": state["value"]})
    return {"value": state["value"] + 1} if decision.get("ok") else {"note": "拒绝"}

graph = builder.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "demo-001"}}
out = graph.invoke({"value": 0}, cfg)
print(out["__interrupt__"])                       # 中断在返回值里，不是抛出
out = graph.invoke(Command(resume={"ok": True}), cfg)
```

三处最容易错：`invoke()` 不抛中断异常，payload 在 `__interrupt__`；恢复不是断点续行，是整个节点重跑；重跑范围是节点，不是整张图。

## 九、人机协同（HITL）

### 9.1 四种决策

| 决策 | 含义 |
|---|---|
| `approve` | 照原样执行 |
| `edit` | 改参数后执行 |
| `reject` | 拒绝，附带理由 |
| `respond` | 不进工具，直接给用户回话 |

第四种最常被漏。用户问「你能帮我发邮件吗」，模型准备调工具，人想说「不用发，告诉我怎么写就行」——这就是 respond。

### 9.2 配置

```python
agent = create_agent(
    model="gpt-4o",
    tools=[search, send_email],
    middleware=[HumanInTheLoopMiddleware(interrupt_on={"send_email": True})],
    checkpointer=saver,          # 必需，没有它中断无处落盘
)
```

三件事同时成立才生效：配了 `interrupt_on`、挂了 checkpointer、恢复时用同一 `thread_id`。

### 9.3 条件中断

不按工具名一刀切，而是按参数判断：金额超阈值、收件人在外域、路径在受保护目录，才中断。

一刀切的代价是审批疲劳：每次都弹，人会盲点同意，护栏等于没有。

### 9.4 子代理与权限中断

多代理时子代理也能配中断，主代理汇总时一并拿到。文件系统类工具可以配成「越权访问自动中断」，比事后报错更早。

### 9.5 生命周期

```text
启动 → 节点执行 → 命中中断 → 存检查点 → 返回 interrupts → 人决策 → resume → 重入节点 → 继续
```

前端要做的三件事：把中断渲染成明确待办、把决策回传、处理超时未决策（会话过期要能告警）。

## 十、踩坑清单

| # | 坑 | 实际 |
|---|---|---|
| 1 | 把 interrupt 当报错处理 | 它是业务断点，不是异常 |
| 2 | 把 `thread_id` 当线程 ID | 它是检查点主键 |
| 3 | 以为检查点默认开 | 不传 checkpointer 什么都不存 |
| 4 | 以为恢复是断点续行 | 整个节点重跑 |
| 5 | 用 try/except 接 `invoke` | 中断在返回值里，接不到 |
| 6 | 把 interrupt 包进 try | 被吞，图卡住 |
| 7 | 多个 interrupt 顺序变动 | 值错位 |
| 8 | payload 塞复杂对象 | 序列化失败 |
| 9 | 以为崩溃不丢状态 | 分档：async 丢一步，exit 全丢，sync 全保 |
| 10 | 硬杀后指望自动恢复 | 硬杀来不及写，无解 |
| 11 | 以为报错会自动转人工 | error_handler 是补偿路由 |
| 12 | 换 `thread_id` 去恢复 | 等于开空线程 |
| 13 | 把静态断点当动态中断 | `interrupt_before` 不带 payload，只适合调试 |

## 十一、演练与验证

### 11.1 故障注入的四个点

| 注入 | 看什么 |
|---|---|
| 节点执行到一半杀进程 | 能否从检查点续，重做几步 |
| 外部写接口超时 | 是否重复写入 |
| 中断后换进程恢复 | 状态是否完整 |
| 连续失败触发熔断 | 是否快速失败而非拖死 |

### 11.2 三个指标

- 恢复成功率：注入十次，成功续上几次。
- 重做步骤数：恢复后实际重跑的节点数。
- 重复副作用次数：外部系统被写了几次。

第三项最容易漏测，也是唯一会造成真实损失的。

### 11.3 一个反直觉的结论

检查点不等于「恰好执行一次」。它只保证「知道从哪继续」，不保证「副作用只发生一次」。后者要靠幂等，二者缺一不可。

## 十二、实验口径与 D11 实测

状态：已跑（2026-11-13，项目 `checkpoint-recovery`）。方向是 D11 长任务断点恢复。

| 项 | 口径 |
|---|---|
| 基线 | 无检查点，失败后整条任务重跑 |
| 增强 | `SqliteSaver` 检查点（durability=sync）+ 幂等副作用注册表 |
| 输入 | 同一组真实语料（总纲段落 5 篇），注入同一组故障（无故障 / 节点异常 / 外写超时 / 外写后硬杀） |
| 主指标 | 恢复成功率、重做步骤数 |
| 次指标 | 恢复耗时、重复副作用次数 |
| 已知代价 | 每次 super-step 落盘有写放大；sync 档延迟明显上升 |
| 失效条件 | 单步任务或可整体重跑且无副作用的场景，检查点收益接近于零 |

### 12.1 对照结果（4 场景 × 2 模式 × 3 次重复）

| 模式 | 场景 | 恢复成功率 | 重做步骤(均) | 外部写(均) | 重复副作用(均) | 幂等拦截(均) | 耗时ms(均) |
|---|---|---|---|---|---|---|---|
| baseline | clean | 100% | 0.0 | 2.0 | 0.0 | 0.0 | 11 |
| baseline | raise@dedupe_merge | 100% | 5.0 | 2.0 | 0.0 | 0.0 | 15 |
| baseline | write_fail@notify | 100% | 5.0 | 3.0 | 1.0 | 0.0 | 16 |
| baseline | crash@write_report | 100% | 5.0 | 3.0 | 1.0 | 0.0 | 4144 |
| enhanced | clean | 100% | 0.0 | 2.0 | 0.0 | 0.0 | 34 |
| enhanced | raise@dedupe_merge | 100% | 3.0 | 2.0 | 0.0 | 0.0 | 50 |
| enhanced | write_fail@notify | 100% | 1.0 | 2.0 | 0.0 | 0.0 | 43 |
| enhanced | crash@write_report | 100% | 2.0 | 2.0 | 0.0 | 1.0 | 3891 |

### 12.2 读表三条

1. **重做步骤**：baseline 恢复 = 整链重跑（恒 5）；enhanced 只重跑失败节点及其后续——crash 场景 2 步、write_fail 1 步、raise 3 步。
2. **重复副作用**：crash@write_report 场景 baseline 必为 1（报告被发布两次）；enhanced 靠幂等拦截为 0，`dup_blocks` 留痕 1 次，这是「dup=0 才有据可查」的原因。
3. **耗时**：enhanced 每步写检查点，clean 场景略慢（34 vs 11ms）；崩溃场景因少重做而更快（3891 vs 4144ms）。

### 12.3 durability 三档同一现场对照

`sync` 崩溃后只重做 2 步；`exit` 硬杀后快照全无，只能整链重做 5 步。默认 `async` 小概率丢最近一步，依赖调度时序、复现不稳定，未量化。

证据：项目 `runs/20261113-022608-experiment/report.md`；机制自测 11/11、端到端 LLM 3/3。项目登记见 [[02-AI/AI专项/流程控制与可靠性/README|模块 README]] 与 [[00-LPK/个人档案/lpk个人简历/项目目录列表|项目目录列表]]。
