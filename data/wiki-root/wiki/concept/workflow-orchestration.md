# 六种工作流编排模式与选型判定

## 总表

| 模式 | 结构 | 适合 | 代价 |
|---|---|---|---|
| 链式 | A → B → C 固定顺序 | 步骤确定的流水线 | 一步错全链停 |
| 路由 | 先分类再分发到不同分支 | 输入类型差异大 | 分类错就全错 |
| 并行 | 多个子任务同时跑，最后汇总 | 子任务互不依赖 | 汇总要处理冲突 |
| 协调者/工作者 | 一个调度者拆任务，多个执行者干 | 任务可拆且异构 | 调度者是瓶颈 |
| 评估者/优化者 | 生成 → 评审 → 再生成 | 质量要求高、可迭代 | 轮数与成本翻倍 |
| 自主循环 | Agent 自己决定下一步 | 开放任务 | 不可预测，要步数上限 |

^[raw/flow-control.md]

## 各自的要点

- **链式**：每步输入输出格式固定，中间产物落盘以便单步重跑；链路超过五步就该考虑并行或拆分。
- **路由**：规则分类便宜确定但覆盖不了新类型，模型分类能泛化但有误判与成本；生产常见做法是规则先挡一层、剩下的交给模型。
- **并行**：分支并行、分片并行、竞争并行三种；合并阶段才是难点——顺序、重复、冲突结论都要显式处理。
- **协调者/工作者**：适合研究与写作这类可拆分且子任务差异大的任务；拆分质量决定上限，协调者不知道该拆什么时工作者再多也没用；token 与延迟随工作者数量线性增长，要设上限。
- **评估者/优化者**：评审标准必须写死，否则每轮意见不同、模型无法收敛；轮数常见 2–3 轮，超过后收益迅速递减。
- **自主循环**：能力最强最不可控，三条约束缺一不可——最大步数、单步超时、总成本上限，缺一条就可能烧穿额度。

## 选型判定树

```text
步骤固定？ ── 是 ── 有分支？ ── 否 → 链式
                          └─ 是 → 路由
          └─ 否 ── 任务可拆？ ── 是 → 协调者/工作者（或并行）
                             └─ 否 ── 质量要求高？ ── 是 → 评估者/优化者
                                                └─ 否 → 自主循环
```

## 编排之外还得管什么

编排模式决定失败会怎么传播（链式一步错全链停、路由分类错就全错），所以选完模式还要配 [[concept-agent-reliability]] 里的失败分类与三道防线，以及 [[concept-checkpoint-recovery]] 的落盘与续跑。引擎层面的 API 与部署不在本页范围；原文区分了「正文讲该用哪种编排」与「引擎手册讲某个引擎怎么装怎么配」，并简列 Temporal（重工作流、持久化执行）、Prefect（数据流水线）、Inngest（事件驱动、Serverless）、Hatchet（轻量 Go 任务队列）、Windmill（脚本与应用自带 UI）、n8n（可视化节点式）、ControlFlow（Agent 为中心）七种定位。^[raw/flow-control.md]
