# RAG 全链路五段取舍

## 零、链路骨架

RAG 是「检索 + 增强 + 生成」三个动作的系统组装，不是模型也不是框架：模型不变，把「它该知道什么」从参数搬到每次调用的上下文里。三模块（检索器 / 增强器 / 生成器）各自失效表现分别是「无依据或旧版本」「挤掉指令或上下文不足」「自由发挥」。^[raw/rag-total.md]

在线七步：查询处理（多轮先做指代消解）→ 相似度检索（Top-K，度量须与建索引一致）→ 重排（可选，候选 20–100）→ 上下文组装（带编号与出处）→ 生成（提示词写死「只依据资料 / 没有就说没有 / 标来源」）→ 后处理（可选，事实核查与格式整理）→ 返回并附来源；严肃场景无来源的答案视为不可用。^[raw/rag-total.md]

离线六环节：加载 → 解析 → 清洗 → 分块 → 向量化 → 入库建 ANN 索引。**解析与分块决定检索上限**，后面重排只能在已入库候选里挑；把力气全花在换 Embedding 上、解析把表格切碎，换模型也没用。^[raw/rag-total.md]

三种相似度度量：余弦（文本检索默认，向量归一化后与内积等价）、欧氏（位置本身有意义时；未归一化会被长度差异主导）、内积（推荐类场景，长度是信号；文本检索里长文本占便宜）。^[raw/rag-total.md]

三条架构路线：2-Step（固定两步，控制力高、可量化对照，**起步一律走这条**）、Agentic（检索是工具，次数不定，对照时说不清是策略好还是多搜了几轮）、Hybrid（查询增强 + 检索验证 + 答案验证）。^[raw/rag-total.md]

## 一、文档解析

- **MinerU Hybrid**（本地 Pipeline 解版面 + 复杂页走 Qwen-VL 的 VLM）：表格与图文混排还原好、适合真实企业 PDF，代价是外部 API 的成本与延迟。^[raw/kb-rag.md]
- **PaddleOCR（PP-OCRv6，GPU）**：中文 OCR 强，注入原解析流程处理扫描件；代价是多一条链路。少量关键页可只走 VLM（上下文理解好，但贵且慢）。^[raw/kb-rag.md]
- **LightRAG / Neo4j 图抽取**：保留实体关系利于推理，不擅长精确原文还原，适合知识图谱型问答。^[raw/kb-rag.md]
- **结构保护**：自研结构感知 NodeParser 保证表格不被切断、指标可对齐；代价是针对场景定制。^[raw/kb-rag.md]

六种输入的对应工具：TXT/MD 直接读；Word 取段落与标题样式（防页眉页脚、批注、目录混入正文）；HTML 正文提取算法（代码块与表格易被压平）；电子 PDF 用 pdfplumber/PyMuPDF 抽文本与坐标；图文混排走 MinerU 类版面模型；扫描件先 OCR；图片图表用多模态模型生成描述后入库，描述质量决定能否被召回。^[raw/rag-total.md]

补充（机制层）：解析错则后面全错且无法补救——表格塌成一行、双栏 PDF 串行、扫描件整页空白。表格三条做法：解析时识别边界、切分时整表成块或按行切且每行重复表头、入库时把表名与列名写进块文本。清洗三件事：去页眉页脚与页码（否则成 BM25 高频噪声）、合并被换行切碎的句子、保留标题层级等结构标记。^[raw/rag-total.md]

中文四特殊：分词边界（专名被切碎，BM25 召不到，需领域词典或字符级 BM25）、全角半角归一、段落无标点（改结构切分）、表格跨页按续表标识合并。^[raw/rag-total.md]

解析质量验收三条：抽二十页看正文连续与串栏、抽五张表看表头与数据是否同块、抽三个扫描页看 OCR 错字率。不验收就入库，是后面所有「召回不准」的根源。^[raw/rag-total.md]

## 二、切分

结构感知切分（按表格/标题保护）语义完整、利于指标定位，实现复杂。chunk 太小召回噪声多、太大稀释相关性；overlap 防边界信息丢失；中文要考虑 BPE tokenizer 对 CJK 的分词影响。^[raw/kb-rag.md]

九种策略的定位（详见 [[source/rag-total]]）：固定长度（会在句中断，适合快速验证）；滑动窗口（重叠 10–20% 够用，半块会让索引体积翻倍）；递归字符切分是工程默认（段落→换行→句号→空格逐级降级，成本极低）；语义切分边界最合理但要多跑一遍 Embedding（适合课程转录、访谈）；按结构切分能说出「出自第三章第二节」但依赖解析质量；父子文档 / Small-to-Big 是「小块检索求准、大块生成求全」，代价是索引体积翻倍且父块过长要再截断；分层索引（句/段/文档三层）适合「先定位在哪节再读那节」；Agentic 分块最贵，只在结构极不规范且文档量小时试。^[raw/rag-total.md]

参数经验值：chunk size 512–1024 token（技术文档偏小保证精度、法规合同偏大保证完整）、overlap 50–100 token（约 10%）、每块至少 100 字（太短易成噪声）、块内元数据写来源/页码/章节路径/文档 ID——引用溯源与元数据过滤都靠它。**按文档类型分组配参数**，不要全库一个参数（合同被切碎、网页留大块）。^[raw/rag-total.md]

分块五个坑：全库一个参数、表格被切断、无重叠、块过长（噪声稀释注意力，超出走父子块）、不带元数据（命中后说不出来源）。^[raw/rag-total.md]

## 三、Embedding 与更新

本地 CUDA 部署 BGE-M3：多语言强、稠密/稀疏/ColBERT 三向量、可离线，代价是 GPU 资源。文档更新走 **collection 版本化重建**（可追溯、可回滚，占空间），而不是全量重灌。^[raw/kb-rag.md]

Embedding 同时作用于索引与查询两端，**两端必须同模型同预处理**，否则向量不在同一空间、结果等于随机。选型五看：MTEB 的 Retrieval 列（别拿分类聚类分选检索模型）、语言覆盖、维度（768–1024 为平衡点，3072 精度略高但存储翻倍、检索变慢）、最大输入与块大小匹配（上限 512 的模型喂 1024 的块会被截断）、部署方式。实践顺序：先用轻量模型跑通，达标后再换大模型看提升是否值得成本。^[raw/rag-total.md]

维度不是越高越好；领域失配（术语向量挤在一起、问法与原文措辞差距大、同义实体多写法）比维度不足更常见。判断法：抽二十对「问题—应命中片段」看 Top-5 命中率，低于六成先怀疑 Embedding 再怀疑切分。微调用对比学习三元组（正样本是真正能回答的片段而非主题相近的片段、负样本取语义相近但不相关的、正负比 1:4 到 1:9），代价是模型与索引绑定、换模型必须整库重建。^[raw/rag-total.md]

增量更新三法：全量重建（大库耗时且期间不可用）、按文档 ID 定点替换（要维护稳定文档 ID）、collection 版本化（空间翻倍但可回滚）。**只加不删是最常见错误**：新旧两版一起被召回，模型可能拿到过期条款。^[raw/rag-total.md]

## 四、检索

向量库见 [[entity/chroma]]（轻量）与 [[entity/qdrant]]、Milvus（分布式、GPU、生产可用，代价是 etcd/MinIO/Pulsar 运维重）。七个库的判断顺序：先看规模，再看要不要自己运维，最后看已有基础设施能否复用。五种 ANN 索引：Flat（精度最高最慢，小库）、IVF（聚类分桶，中等规模）、HNSW（当前默认，最快且精度高）、PQ（量化压缩，内存吃紧的超大库）、DiskANN（落盘，十亿级）。HNSW 三参数 M（16–64）/efConstruction（128–512）/ef（线上唯一该调的，取 limit 的 4–10 倍起步），前两个改了要重建索引。^[raw/kb-rag.md]^[raw/rag-total.md]

选型现实建议：单机验证用 Chroma 或 FAISS，生产用 Milvus 或 Qdrant，已有 Postgres 且规模不大可上 pgvector 省一个组件（代价是索引算法不如专用库丰富）。建库与查询的 `dimension`、`metric_type` 必须对齐，`output_fields` 要带正文与来源否则命中后还得回查。^[raw/rag-total.md]

检索层默认配置见 [[concept/hybrid-retrieval]]：向量管语义改写、BM25 管精确串、RRF 融合、交叉编码器把「像」变成「对」；四段流程是 topM → topN → RRF topP → Rerank topK(3–8)，粗排负责召回率、精排负责准确率。查询侧四种加工的判断顺序：先改写（最便宜收益最稳）、再拆分（复合问题）、最后 HyDE（收益大风险也大）。^[raw/kb-rag.md]^[raw/rag-total.md]

先按元数据过滤再检索，比检索后过滤省一个数量级；检索后过滤等于白算。分区按业务或时间切，分区键选错等于白做（查询总跨类型就没收益）。多库隔离三档：独立 collection（隔离最强，管理成本随租户线性涨）、命名空间（部分库支持不完整）、元数据字段（弱，一条漏过滤就越权）。^[raw/rag-total.md]

**召回没捞到的，重排救不回**：先看 Recall 再看排序；多跳问题单条打分不够，要靠查询拆分或图检索（见 [[entity/graphrag]]）。^[raw/rag-total.md]

## 五、管理与引用

多库隔离用 collection 级 + 版本化：互不污染、可回滚，管理变复杂。引用溯源维护 chunk↔原文页码映射，前端高亮/跳转；金融与 ESG 严谨场景必须可核查，代价是额外维护映射。^[raw/kb-rag.md]

## 六、组装、生成与多轮

组装四件事：排序位置（长上下文有 U 型注意力谷底，高分块交替放首尾）、体积控制、来源编号（每段带编号与出处）、多样性去重（MMR，lam=0.5 在保相关前提下压重复）。^[raw/rag-total.md]

预算分配经验：片段不超过一半、历史不超过四分之一、其余留指令与输出；逼近上限时先压历史、再压片段、最后动指令。提示词四条规则缺一不可：没有就说没有（防幻觉）、每句标编号（可溯源）、不补资料外事实、控制语言与篇幅。模型会引用不存在的编号，这本身是幻觉的一种。^[raw/rag-total.md]

**拒答与召回是一对**：召回不足时守规则的模型大量拒答，放开规则又开始编，须按置信度分三层（直接答 / 答并标注依据有限 / 明确拒答并给建议）。置信度可用最高重排分数、命中块数量、命中块分散程度合成。生成侧四种优化：流式（改善感知延迟不改变总耗时）、答案缓存（知识更新要清）、上下文压缩（会丢细节）、结构化输出。^[raw/rag-total.md]

多轮失效的原因不在检索算法，而在「它」脱离上下文本身歧义。三条做法：历史拼进查询（噪声变多）、**先改写独立查询（工程默认，多一次模型调用）**、对话状态加槽位。状态记三样：已确认事实、当前目标、已排除选项。超过五轮就压，优先压背景、保已确认参数。^[raw/rag-total.md]

## 七、性能与成本

四个瓶颈按耗时排序：查询向量化（几十 ms）→ ANN 检索（几到几十 ms）→ 重排（百 ms 级）→ 生成（秒级占大头）。**绝大多数「RAG 很慢」的瓶颈在生成不在检索**，先测再优化。降本顺序：先把注入块数从十降到五，再把生成模型换小模型试效果，最后才考虑缓存与蒸馏；成本四块里前两块（查询 Embedding、检索重排算力）通常可忽略，注入与生成 token 是大头。^[raw/rag-total.md]

## 串起来的一句话

选型逻辑始终是「看数据规模、是否要离线、运维成本」三件事，而不是比谁更先进。^[raw/kb-rag.md]
