# Agent 可靠性：四类失败、三道防线与重试纪律

## 为什么 Agent 不能只靠「重试 + 事务」

普通服务单次执行毫秒到秒、无状态、失败多为确定性原因、副作用有事务保证。Agent 单次执行秒到小时、有状态、失败里还有模型判断错与工具选错、可以中途停下等人、副作用落在事务管不到的外部系统。因此可靠性要在重试与事务之外再加一层：**可中断、可恢复、副作用可重放**。^[raw/flow-control.md]

## 四类失败

| 类型 | 例子 | 能否自动重试 |
|---|---|---|
| 瞬时故障 | 网络抖动、下游 429、超时 | 能，退避重试 |
| 永久故障 | 参数非法、鉴权失败、资源不存在 | 不能，重试只是浪费 |
| 语义故障 | 工具选错、参数指向错对象 | 不能，要改判断 |
| 编排故障 | 节点卡死、循环不收敛、状态不一致 | 要超时与步数上限兜底 |

**只有第一类值得重试**；把其余三类丢进重试，结果是延迟放大、账单上升、问题依旧。^[raw/flow-control.md]

另有一个按位置的切法（入口/处理/输出三类错误），意义同样是定位：入口错误不该进重试，输出错误不该在模型侧调参数。^[raw/flow-control.md]

## 三道防线

`预防（执行前）→ 检测（执行中）→ 恢复（失败后）`，三条同时存在才叫可靠；只有预防等于赌不会出事，只有恢复等于每次都重跑。^[raw/flow-control.md]

- 预防：输入校验、工具白名单、输出格式写死并给合法示例、单次调用 token 与步数预算。
- 检测：JSON 可解析与字段齐全、空结果/全零/异常值、单步耗时告警、同工具同参数重复调用检测。
- 恢复：重试（延迟放大）、降级（质量下降）、换路（要预先备路）、人工接管（依赖人力）、回滚（要能撤回）。

三种容错机制覆盖不同层面：冗余（关键路径有备份，如双供应商、双区域）、隔离（单工具失败不拖垮整轮）、监控（成功率、延迟、错误类型分布）。^[raw/flow-control.md]

## 四种手段的分工与三条重试纪律

超时只管无限等待、不管慢而终成功；重试只管瞬时故障、遇到永久故障会放大损失；熔断只管持续失败还继续打、救不了已经失败的这一次；降级只管依赖不可用、带来质量损失。^[raw/flow-control.md]

重试三纪律：只对可恢复异常重试；次数设上限、间隔指数退避加抖动；重试前先判幂等，非幂等操作不能盲目重试。熔断到阈值后隔段时间放一个探针试探，否则下游挂掉会把上游连接池与线程池一起拖死。降级必须显式告知，否则用户以为拿到的是完整结果。^[raw/flow-control.md]

## 与幂等、检查点的关系

重试与恢复都会让同一逻辑执行两次，所以幂等是重试的前提（见 [[concept-idempotency]]）。而恢复到哪一步由检查点决定，但检查点只保证「知道从哪继续」，不保证「副作用只发生一次」（见 [[concept-checkpoint-recovery]]）。^[raw/flow-control.md]

## 实战落点

演练要注入四个点：节点执行到一半杀进程、外部写接口超时、中断后换进程恢复、连续失败触发熔断；看三个指标：恢复成功率、重做步骤数、重复副作用次数——第三项最容易漏测，也是唯一造成真实损失的。^[raw/flow-control.md]
