# 本体论（Ontology）：语义层与执行层

## 定位：换一层，不是演进线的第三代

RAG / GraphRAG / Ontology 三者可以叠在一个系统里，但**不是同一条演进线的三代**。前面所有链路回答的是「怎样取证」，本体回答的是另一个问题：**业务对象怎样表达、允许怎样改变**。^[raw/rag-total.md]

| 能力 | 主要问题 | 成本与边界 |
|---|---|---|
| 普通 RAG | 从资料里找依据，给生成补上下文 | 召回、解析、更新、权限都要维护；向量检索只是其中一条实现路线 |
| GraphRAG | 从语料抽图、生成社区摘要，用关系与汇总结构增强查询 | 建图、消歧、更新有成本；图上有关系不保证业务结论正确，官方也保留普通检索路径 |
| Ontology | 把已集成的数据组织成业务对象、关系与受控操作 | 要维护数据映射、业务逻辑、权限与执行集成，是业务与数据治理投入 |

^[raw/rag-total.md]

## 通用本体 vs 运营本体

- **通用本体**：[W3C OWL 2](https://www.w3.org/TR/owl2-overview/) 定义类、属性、个体与形式语义，给的是**建模能力**，推不出审批、审计或业务系统回写。
- **运营本体**：[Palantir Ontology](https://www.palantir.com/docs/foundry/ontology/overview/) 是产品层面的定义，建立在已集成的数据集、虚拟表与模型之上，分两块：
  - **语义部分**：对象、属性与关系，统一「这是什么、与什么有关」。
  - **执行部分**：Action Types、Functions 承接业务操作与计算逻辑，配合平台权限、应用限制与治理。

^[raw/rag-total.md]

**一项业务动作能否执行，取决于四件事同时成立：定义了规则、绑定了实现、配置了权限、底层系统支持。** 只把对象命名清楚，一步都没到。^[raw/rag-total.md]

## 两类 MCP：最容易混的一处

| 官方入口 | 面向谁 | 能力与边界 |
|---|---|---|
| Ontology MCP | 业务使用者与消费业务能力的 Agent | 把应用的 Object Types、Action Types、Query Functions 暴露为 MCP tools；可读对象、执行预定义 Action、运行查询，受应用限制约束 |
| Palantir MCP | 构建本体与应用的开发者、编码 Agent | 可修改本体类型、开发应用、操作数据集与转换；官方明确它**不能写入实际 Ontology 业务对象数据** |

^[raw/rag-total.md]

「允许修改本体结构」与「允许执行业务动作」必须**分别授权**。MCP 只提供调用接口，权限与业务约束仍由服务及平台落实。两份官方概览能证明能力存在，但**未给出明确 GA 日期**，不要引用「某年正式 GA」这类表述。^[raw/rag-total.md]

## 落到具体项目的三问

先查三件事（不等同于要上独立本体层）：^[raw/rag-total.md]

1. 同一个对象在不同系统里能否对齐身份，指标口径有没有统一来源。
2. 每个写操作是否明确参数、状态前提、权限与返回结果，而不是给模型一个任意改表入口。
3. 操作是否有审批条件、幂等处理、失败恢复与审计，能否从执行结果验证状态变化。

这三项在已有领域模型与业务服务里就能落实。要不要加独立本体层，由跨系统语义复用与治理需求决定，不由「别人都在讲 Ontology」决定。^[raw/rag-total.md]
